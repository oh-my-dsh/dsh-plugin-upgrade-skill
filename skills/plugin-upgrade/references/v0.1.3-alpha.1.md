### DSH-0.1.3-A1-01 · Session persistence API is now lifecycle-held: `create()`/`open()` return `Promise<SessionHandle>`, and one session is held by at most one process

- **Type**: breaking
- **Applies to**: plugins that call `ctx.sessionPersistence` or the agent-loop create surface directly; presets/patches that assume synchronous session creation
- **Touchpoints**: #2 (host service consumption)
- **Action level**: required-if-hit
- **Symptoms**: the release notes name it "Session persistence API 改为由生命周期持有的 `SessionHandle`；`agentLoop.create()` 改为异步，新增 session 锁，同一 session 至多被一个进程持有". Concretely: `@deepseek-ai/dsh-session-persistence` now hands out `SessionHandle` from async `create()`/`open()` (the checkpoint-policy contract test at `packages/session/session-checkpoint-policy/tests/session-checkpoint-policy.spec.ts:17` types both as `Promise<SessionHandle>`), the JSONL backend implements it as `JsonlSessionHandle` with per-handle mutation chains and single-flight drains (`packages/session/session-persistence-jsonl/README.md`), and a session lock means a second process holding the same session no longer silently concurrent-writes.
- **Migration recipe**:
  1. `grep -rn "sessionPersistence" <plugin src>` — every call site that consumed a synchronous handle now awaits; sequencing that assumed create-then-use in one tick must become async.
  2. If the plugin opened the same session log from a side process (a projector, an exporter), stop: the lock makes the second holder fail. Read through the session-query/projection surfaces instead of a private handle.
  3. Host-plane plugins: treat the handle as lifecycle-owned — do not stash it across teardown; re-open on remount.
- **Verification**: typecheck against the 0.1.3-alpha.1 cohort fails on any unchanged synchronous call site; a boot + open-session round-trip on the new host shows no lock errors for a single holder.
- **Source**: [0.1.3-alpha.1 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.3-alpha.1) (破坏性变更 bullet) · `packages/session/session-checkpoint-policy/tests/session-checkpoint-policy.spec.ts` · `packages/session/session-persistence-jsonl/README.md` at `dsh-v0.1.3-alpha.1`

### DSH-0.1.3-A1-02 · Session format v2: committed v0/v1 logs migrate through an adjacent generation on read; raw-JSONL readers must speak v2

- **Type**: breaking
- **Applies to**: plugins that parse session `.jsonl` files directly (log exporters, auditors, custom projectors) instead of reading through session-query/projection services
- **Touchpoints**: #6 (durable/file boundary)
- **Action level**: required-if-hit
- **Symptoms**: `SESSION_FORMAT_VERSION` is now `2` (`packages/core/session/src/types.ts:86` at `dsh-v0.1.3-alpha.1`); the header check rejects any other version (`packages/core/session/src/index.ts:101`). Old v0/v1 logs are not rewritten in place — they migrate into a version-named successor generation **adjacent** to the committed file (the [adjacent-migration policy](https://github.com/deepseek-ai/deepseek-harness/blob/main/.agents/notes/implemented/architecture/2026-08-31-released-session-format-migrations.md): body reads may add a successor, never move/overwrite/delete committed generations). Assistant streams also aggregate into persisted settlements per attempt on the v2 side.
- **Migration recipe**:
  1. A raw reader that handled v1 must add v2 parsing and follow the generation layout: on encountering a v0/v1 log, expect the migrated v2 generation to appear next to it after first read.
  2. Do not build on "the old file disappears" — it does not; pick the newest generation.
  3. Prefer the supported route: read through `@deepseek-ai/dsh-session-query` / projection services, which absorb the version bump.
- **Verification**: open a pre-0.1.3 session on the new host (migration happens on read); confirm the original log is intact and the reader sees the v2 generation. Note the release notes' **known perf regression on historical-session loading** when sizing the check.
- **Source**: [0.1.3-alpha.1 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.3-alpha.1) ("Session format 升级至 v2… 不可变的相邻 generation 迁移") · `packages/core/session/src/types.ts:86` · `packages/core/session/src/index.ts:101` at `dsh-v0.1.3-alpha.1`

### DSH-0.1.3-A1-03 · 0.1.3-alpha.1 rides the unpublished cohort: verify on a source-launched host while npm has no tarball

- **Type**: behavior
- **Applies to**: any plugin declaring compatibility with 0.1.3-alpha.1 before the npm publish lands
- **Touchpoints**: none (environment)
- **Action level**: required-if-declaring-support
- **Symptoms**: measured 2026-09-04, neither the umbrella (`npm view @deepseek-ai/dsh@0.1.3-alpha.1` → 404; `latest`/`next` = 0.1.2-rc.1) nor sub-packages are on npm, so neither `npm i -g` nor registry-pinned verification can reach this version yet.
- **Migration recipe**:
  1. Point the source junction at a checkout of the tag (`git fetch <official url> tag dsh-v0.1.3-alpha.1 && git checkout dsh-v0.1.3-alpha.1`), then `pnpm install && pnpm run build`. **`pnpm run clean` before the first build** — stale `lib/types` from the previous tree breaks tsdown with `MISSING_EXPORT` on constants that moved.
  2. Launch the host from source: `pnpm dsh web` in the checkout (tsx ESM launch; `node apps/cli/lib/bin.js -V` should print the new version after build). Keep the global npm install untouched as the rollback lane.
  3. Plugins whose devDependencies link `~/.dsh/source/current` follow the junction automatically — re-run their typecheck/build/tests against the new tree before declaring support.
- **Verification**: `-V` prints the tag version; the web client boots on the source host; plugins load from the unchanged profile (junction installs need no sync).
- **Source**: [tag dsh-v0.1.3-alpha.1](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.3-alpha.1) · first-hand 2026-09-04 (Windows): checkout `d347e70390`, clean-rebuild, `pnpm dsh web`, six-plugin fleet green — the same unpublished-cohort pattern as [rollup-0.1.2.md](rollup-0.1.2.md) R-01, now on the host side.

### DSH-0.1.3-A1-04 · Web composer/upload and tool-card surfaces churn without a client API change — input-area plugins re-verify at runtime

- **Type**: behavior
- **Applies to**: plugins mounting into `conversation.input.*` slots or rendering tool cards (attachment/preview areas)
- **Touchpoints**: #3 (client slot registration) — unchanged API, changed neighborhood
- **Action level**: conditional
- **Symptoms**: 0.1.3-alpha.1 reworks the upload pipeline (arbitrary file types, files and images sharing one preview area, background upload progress/cancellation) and makes `read_image` tool cards render images inline. None of this changes client slot or facade APIs — but a plugin that overlays, measures, or depends on the composer's DOM structure can break purely by layout.
- **Migration recipe**:
  1. No code action expected; typecheck/build green does **not** cover this risk — the surface is runtime-only.
  2. On the new host, exercise the plugin's real interaction (paste, hover previews, dock, chip) before declaring support. First-hand: a paste/composer plugin (`conversation.input.left`, attach-button integration) crossed this edge unchanged at v0.1.19.
- **Verification**: manual runtime pass on the source-launched host (see card 03): paste image/text, open preview/viewer, confirm slot placement.
- **Source**: [0.1.3-alpha.1 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.3-alpha.1) ("Web 支持上传任意类型的通用文件…", "`read_image` … 在 Web 工具卡中直接渲染图片") · first-hand paste-input verification 2026-09-04.

## Corridor verification record

`pnpm dsh web` from the checkout, global npm left at 0.1.2-rc.1 as rollback.

  only), the Python SDK, headless/ACP products, and the v0/v1 → v2 migration path on real legacy
  logs (the host opened only post-rc.1 sessions during the pass).

## Conclusion

The rc.1 → 0.1.3-alpha.1 edge is the first carded breaking edge of the 0.1.3 series, and its
breaks concentrate on the host/session plane: persistence handles, the session lock, and the v2
format. Pure client-UI plugins ride it for free (verify the composer neighborhood per card 04);
host-plane and raw-log consumers must work cards 01–02. Treat the perf regression on historical
sessions as expected behavior until the next release.
