### DSH-0.1.7-A1-01 · Client UI primitives icon set renamed: every `*16` export is gone

- **Type**: breaking
- **Applies to**: client plugins rendering primitives icons (Web surface)
- **Touchpoints**: none (the host `dsh-client-ui-primitives` static module's export surface)
- **Action level**: required-if-hit
- **Symptoms**: a slot contribution that destructures any `Icon...16` named export gets `undefined` and crashes on render with React error #130 (element type invalid); the framework's slot-level error boundary unmounts the WHOLE slot entry, so the user-visible symptom is an entire surface (dock, header widget) silently vanishing with one minified console error and no request failures. First-hand fleet evidence (2026-09-22, `dsh-ui-progress` on Windows/Edge): the resident input-dock progress strip disappeared after the host upgrade; the crash surfaced in `conversation.input.dock` and the four destructured `*16` icons were the only breakage.
- **Migration recipe**: enumerate every named import from `@deepseek-ai/dsh-client-ui-primitives` in the plugin source; for each `...16` icon, look up the replacement in the target tag's primitives export surface (the 0.1.7 set observed: `IconDatabaseOutline16` -> `IconDatabaseOutlineMedium`/`IconDatabaseOutlineRegular`, `IconLoadingOutline16` -> `IconLoadingOutlineMedium`/`...Regular`, `IconWarningOutline16` -> `IconWarningOutlineMedium`/`...Regular`, `IconSparkle16` -> `IconSparkleMedium`/`...Regular`; re-check the target tag - the variant split may widen). Plugins that must run on both pre- and post-rename hosts resolve the component at runtime through a fallback chain (`*16` -> `*Medium` -> `*Regular`) instead of static named imports, and extend their unit-test module mocks with every fallback name (strict module mocks throw on undefined-export access, which masks the real failure).
- **Verification**: in a driven browser against the upgraded host, assert all three: the surface's DOM marker is present, zero `slot entry crashed` console records, and the expected network requests fire. A single "CSS loaded, no errors" check has false negatives.
- **Source**: [dsh-v0.1.7-alpha.1 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.7-alpha.1); primitives export surface at tag `dsh-v0.1.7-alpha.1` (`@deepseek-ai/dsh-client-ui-primitives`); first-hand: dsh-external/dsh-ui-progress v0.10.3.

### DSH-0.1.7-A1-02 · `workspaceFiles` reads unify on `readBytes`

- **Type**: breaking
- **Applies to**: client/server plugins reading workspace file content through the `workspaceFiles` Remote namespace
- **Touchpoints**: #4 (Remote namespace calls) or direct service calls
- **Action level**: required-if-hit
- **Symptoms**: reads through the retired read methods stop working (or fail type checks at build time against the new host types).
- **Migration recipe**: the release notes state the direction only (workspace file reads unify to readBytes; plugins must migrate the old interface) - do NOT invent call signatures: open `@deepseek-ai/dsh-api-workspace-files` at tag `dsh-v0.1.7-alpha.1` (Remote types + Host service) and migrate each old read call to the `readBytes` contract (parameter shape, return envelope, chunking) from the tag's declared types. Grep the plugin for `workspaceFiles.read`, `readAll`, `readText`, `readRelated` and re-derive each against the tag.
- **Verification**: exercise one real file read through the migrated path against a 0.1.7 host and assert the bytes match the on-disk file.
- **Source**: [dsh-v0.1.7-alpha.1 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.7-alpha.1); `@deepseek-ai/dsh-api-workspace-files` types at tag `dsh-v0.1.7-alpha.1`.

### DSH-0.1.7-A1-03 · Settings move into the current Profile's plugin configuration

- **Type**: breaking
- **Applies to**: plugins that persist user settings, and any plugin reading the legacy global settings file
- **Touchpoints**: #6 (settings/config surfaces), profile files
- **Action level**: required-if-hit
- **Symptoms**: settings written through the legacy global settings file stop being read after the one-time import; live edits to undeclared fields do not reach a running plugin.
- **Migration recipe**: per the release notes, settings are now saved through the current Profile's plugin configuration and the legacy settings.yaml is attempted exactly once - verify after upgrading that the values the plugin depends on actually landed in the new store (do not assume the import covered plugin-specific namespaces). If the plugin ships its own settings plugin/config surface, declare its fields so no-reload live updates apply; re-check the declaration mechanism against tag `dsh-v0.1.7-alpha.1` types before shipping.
- **Verification**: change one plugin setting in the UI, restart the host, assert the value survives; and confirm the one-time import carried the plugin's previously stored values.
- **Source**: [dsh-v0.1.7-alpha.1 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.7-alpha.1).

### DSH-0.1.7-A1-05 · Session log format V4 with a batch migration tool

- **Type**: behavior
- **Applies to**: plugins that parse session log files directly; everyone else via host compatibility
- **Touchpoints**: none (session persistence plane), or direct log parsing in the plugin
- **Action level**: conditional
- **Symptoms**: none for plugins that read session data through host services; direct log parsers may meet V4 records (including turn-end records synthesized for compatibility with some V3 sessions).
- **Migration recipe**: if the plugin parses raw session logs, re-check the V4 record shapes at tag `dsh-v0.1.7-alpha.1` and the batch migration tool the release ships; prefer routing reads through host services so format versions stay an implementation detail. Per the released session-format status, versions are additive generations - never write down-version.
- **Verification**: open a migrated V4 session and a not-yet-migrated V3 session; both render through the plugin's read path.
- **Source**: [dsh-v0.1.7-alpha.1 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.7-alpha.1); session-format status doc in the harness repository.

### DSH-0.1.7-A1-08 · Tolerant Profile loading: unreadable optional bundles no longer abort the Profile

- **Type**: behavior
- **Applies to**: profile composition; every installed plugin's failure visibility
- **Touchpoints**: none (loader behavior)
- **Action level**: informational
- **Symptoms**: a plugin whose package cannot be read no longer crashes the whole boot; the Profile loads without it, the Plugin Manager keeps the error plus disable/remove controls.
- **Migration recipe**: none for the plugin. Two awareness items for fleet maintainers: (1) after a host upgrade, a plugin can be MISSING rather than crashing the boot - check the Plugin Manager page / boot roster instead of assuming no crash means all loaded; (2) this is load-level tolerance only - a plugin that loads but fails activation can still vanish a slot silently (see DSH-0.1.7-A1-01), so keep the fail-loud diagnosis habit.
- **Verification**: on a profile with one deliberately broken bundle, boot succeeds and the Plugin Manager shows the error entry.
- **Source**: [dsh-v0.1.7-alpha.1 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.7-alpha.1).

### DSH-0.1.7-A1-10 · Attachments stored only in custom events are no longer auto-read or exported

- **Type**: breaking
- **Applies to**: plugins that store attachment payloads in custom session events
- **Touchpoints**: #5 (session events / projections)
- **Action level**: required-if-hit
- **Symptoms**: attachment payloads that exist only inside a plugin's custom events are no longer read back or included in exports - the plugin must own their storage and reading.
- **Migration recipe**: per the release notes this is a declared adaptation duty: give the plugin its own durable storage for such attachments (or reference host-delivered attachments instead of duplicating payloads into custom events); re-check the event/export boundary at tag `dsh-v0.1.7-alpha.1` before shipping. Audit existing sessions for payloads that would silently drop on export.
- **Verification**: create a session with such an attachment, export the session, and assert the plugin's data survives the export/import round trip (or is intentionally excluded with a surfaced reason).
- **Source**: [dsh-v0.1.7-alpha.1 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.7-alpha.1).
