### DSH-0.2.2-A3-01 · Context menus unify across right-click and keyboard: `MenuTarget` → `ContextMenuTarget`, injected `menuTarget` → `contextMenuTarget`, icons become keyed `contextMenu.icon` slot registrations

- **Type**: breaking
- **Applies to**: client plugins that inject into workspace/sidebar context menus or read the injected menu target
- **Touchpoints**: client slot registry (`contextMenu.icon`), injected-source consumers (`useMenuTarget`)
- **Action level**: conditional
- **Symptoms**:
  - `@deepseek-ai/dsh-client-ui-context-menu/client` no longer exports `MenuTarget` (renamed `ContextMenuTarget`, aligned with `ContextMenuTargetMap`); no compat alias is kept.
  - The injected `menuTarget` / `useMenuTarget` pair is renamed `contextMenuTarget` / `useContextMenuTarget`.
  - Action icons no longer accept React nodes: pass `{ key, src? }` and register the icon component under the keyed slot `contextMenu.icon`; uninstall must clean the registration up.
- **Migration recipe**:
  1. Rename imports/usages per the upstream guide (`MenuTarget`→`ContextMenuTarget`, `menuTarget`→`contextMenuTarget`, `useMenuTarget`→`useContextMenuTarget`).
  2. Replace icon elements with `{ key: '<plugin>.action' }` descriptors; register the renderer via `ctx.slots` under `contextMenu.icon` and dispose on unload.
  3. Rebuild the client bundle; typecheck catches the renames; open a menu to confirm icons render and disappear after plugin disable.
- **Verification**: grep the client bundle for `MenuTarget` / `useMenuTarget` — zero hits expected; both mouse right-click and keyboard menu paths open with plugin entries.
- **Source**: upstream guide [context-menu-target](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.2-alpha.3/docs/upgrade-guide/v0.2.2-alpha.2/context-menu-target/guide.zh.md)（本窗口落地）; [release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.2-alpha.3)（"支持统一右键与键盘菜单……并支持开发者扩展"）; commits `refactor(client): render context menu icons through keyed slots`, `refactor(context-menu): inject shared trigger bindings through slots`.

### DSH-0.2.2-A3-02 · pi-ai request headers are plugin-preparable per session and purpose; invalid headers fail before the request leaves the host

- **Type**: capability
- **Applies to**: plugins integrating providers through pi-ai, and plugins that customize requests
- **Touchpoints**: LLM request preparation seam
- **Action level**: optional
- **Symptoms**:
  - Plugins may now provide dynamic request headers per session and per request purpose.
  - Headers that fail validation abort the request **before** it is sent — a plugin that previously shipped malformed headers silently now surfaces an explicit pre-send error.
- **Migration recipe**:
  1. If the plugin injected static headers by patching provider config, move to the prepared-headers seam so per-purpose values stay correct.
  2. Add a unit check that the header factory never emits empty names/values; the host will now reject them loudly.
- **Verification**: trigger one request per purpose the plugin serves; confirm headers arrive and malformed test headers raise a pre-send error (not a provider 4xx).
- **Source**: [release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.2-alpha.3)（"pi-ai 支持插件按会话和请求用途提供动态请求头；无效请求头在请求发出前报错"）; commit `feat(llm): allow plugins to prepare pi-ai request headers`; upstream guide `llm-request-purpose-declarations`.

### DSH-0.2.2-A3-03 · pi-ai image-count overflow now omits the oldest images and retries, instead of failing the whole request

- **Type**: behavior
- **Applies to**: any plugin whose sessions attach many images (paste-input pipelines, vision workflows)
- **Touchpoints**: LLM request assembly
- **Action level**: informational
- **Symptoms**:
  - Previously a request carrying more images than the model's per-request limit failed outright; now the earliest images are dropped automatically and the request proceeds.
  - Plugins that retried on this failure themselves can retire that retry branch — the host handles it.
- **Migration recipe**:
  1. Remove client-side "too many images" fallback retries; keep any user-facing notice that images were omitted if the workflow needs the audit trail.
- **Verification**: send a request with limit+2 images; expect success with the oldest two omitted (check the provider request payload).
- **Source**: [release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.2-alpha.3)（"通过 pi-ai 接入的模型在会话图片超过请求数量上限时，自动省略最早的图片并继续请求"）; upstream guide `pi-ai-request-image-count`.

### DSH-0.2.2-A3-04 · Cordis Core 4.0.0-rc.11 / Loader 1.0.0-rc.8 / Include 1.1.1: unified config access, entry change events, persistence behavior; loader entry trees validated

- **Type**: behavior
- **Applies to**: every plugin — Cordis is the runtime everything mounts through
- **Touchpoints**: manifest loading, config read/write paths, entry lifecycle
- **Action level**: informational
- **Symptoms**:
  - Config access, entry change, and persistence semantics were unified across the Cordis trio; plugins reading config through non-unified paths may observe different change-event timing.
  - Loader entry trees are now validated (`cordis-loader-entry-trees` guide) — malformed entry manifests that previously loaded leniently can be rejected at boot.
- **Migration recipe**:
  1. Run the plugin's boot smoke on the new host; if config-change events feel different, route reads/writes through the documented unified access instead of raw stores.
  2. Check the plugin manifest against the entry-tree rules in the upstream guide.
- **Verification**: boot the profile, toggle a plugin config value, confirm the plugin observes the change once with the expected payload.
- **Source**: [release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.2-alpha.3)（"同步 Cordis Core 至 4.0.0-rc.11、Loader 至 1.0.0-rc.8、Include 至 1.1.1，统一配置访问、条目变更和持久化行为"）; upstream guides `cordis-loader-entry-trees`.

### DSH-0.2.2-A3-05 · Plugin Manager grows settings-page navigation icons (with uninstall restore) and honest install-failure diagnostics that distinguish install vs enable failures

- **Type**: capability
- **Applies to**: every published plugin (manager UX), plugins with settings pages
- **Touchpoints**: plugin settings seat; plugin-manager install surface
- **Action level**: optional
- **Symptoms**:
  - A plugin may provide a navigation icon for its settings page; uninstalling restores the default icon (registrations are cleaned up).
  - Install failures now show complete diagnostics with a Host-log entry, and **install failure is distinguished from post-install enable failure** — previously both read as one opaque failure.
- **Migration recipe**:
  1. Optional: register a settings nav icon if the plugin has a settings page.
  2. When users report "install failed", check which of the two states the dialog names; enable failures point at plugin code, install failures at the package/channel.
- **Verification**: install a known-good and a known-broken plugin; the dialog should name the correct failure stage each time.
- **Source**: [release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.2-alpha.3)（"插件可为自己的设置页面提供导航图标，卸载后恢复默认图标"、"插件安装失败时显示完整诊断与 Host 日志入口，并区分安装失败和安装后启用失败"）; commits `fix(plugin-manager): claim only what the failed install's answer proves` 等.

### DSH-0.2.2-A3-06 · File read-before-write and external-modification guards default OFF; sandbox restrictions and Review unchanged; profiles may restore the observation policy explicitly

- **Type**: behavior
- **Applies to**: plugins that write files through the fs capability, and profiles relying on the old guards
- **Touchpoints**: fs observation policy
- **Action level**: conditional
- **Symptoms**:
  - The read-before-write check and external-modification watch no longer run by default; writes proceed without the stale-read guard.
  - Sandbox restrictions and the Review flow are **unchanged** — this is only the observation layer.
  - Profiles that want the original guard must opt back into the observation policy explicitly.
- **Migration recipe**:
  1. Do nothing for most plugins. If a workflow depended on rejecting externally-modified files, restore the observation policy in the profile.
  2. Update any test that asserted a stale-read rejection — it will now succeed silently unless the policy is restored.
- **Verification**: with defaults, modify a file externally then write through the plugin — the write succeeds; with the policy restored, the old rejection returns.
- **Source**: [release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.2-alpha.3)（"文件修改的先读和外部修改防护默认关闭，沙箱限制和 Review 保持不变"）; upstream guide `fs-observation-policy-default-off`.

### DSH-0.2.2-A3-07 · Scheduled tasks move to host-level management and the Git worktree entry merges into change requests; the standalone worktree bundle must be removed; `apply_patch` lands default-off

- **Type**: capability
- **Applies to**: profiles carrying the experimental worktree bundle; plugins automating scheduling or patch flows
- **Touchpoints**: profile bundle list (`dsh.profile.bundles`); scheduled-task surface; tool registry
- **Action level**: conditional
- **Symptoms**:
  - The "Git 工作树" entry is merged into "变更请求与工作树"; profiles that enabled the standalone worktree plugin must remove `@deepseek-ai/dsh-experimental-tool-worktree` from `dsh.profile.bundles` manually.
  - Scheduled tasks are managed at host level (manual create, edit, prefilled-prompt create, draft retention, conflict review, reuse-or-new session choice).
  - A new `apply_patch` tool does multi-file add/edit/delete/move in one call and shows in Review; it ships **default off**.
- **Migration recipe**:
  1. Remove the worktree bundle line from the profile; use the unified change-request entry.
  2. Plugins that drove scheduling through session prompts can adopt the host-level task surface instead.
  3. `apply_patch` needs explicit enablement; plugins with their own multi-file patch tools should decide which one the agent sees to avoid duplicate paths.
- **Verification**: dump the profile config; no worktree bundle line remains; the change-request UI opens with the file tree; `apply_patch` is absent from the tool list until enabled.
- **Source**: [release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.2-alpha.3)（"「Git 工作树」入口已合入「变更请求与工作树」……需手动移除"、"「自动化任务」改为统一的宿主级管理"、"新增默认关闭的 `apply_patch` 工具"）; upstream guides `forge-worktree-entry`, `forge-git-permissions`.

### DSH-0.2.2-A3-08 · Six-plugin fleet verification on 0.2.2-alpha.3 (first-hand) + npm interrupted-install recovery runbook

- **Type**: fix
- **Applies to**: maintainers upgrading a plugin fleet to alpha.3; anyone installing the host via npm on Windows
- **Touchpoints**: host install; fleet compatibility declarations
- **Action level**: informational
- **Symptoms**:
  - All six maintained plugins (`dsh-paste-input` 0.2.18, `dsh-file-trace` 0.4.2, `dsh-input-history` 0.1.31, `dsh-ui-progress` 0.11.14, `dsh-ui-whale` 0.3.35, `dsh-minigames` 0.11.1) boot and run on alpha.3 with **zero code changes** — the only required action per plugin was adding the `0.2.2-alpha.3` row to its compatibility ledger and re-stamping the release. Slots, optional services, and remote APIs the fleet uses all resolve.
  - **Interrupted npm install poisons the host in two layers**: (1) the bin shims (`dsh`, `dsh.cmd`, `dsh.ps1`) are left as rename residue (`.dsh-XXXXXXXX`) so the command disappears from PATH; (2) more subtly, a dependency can be half-extracted (`openai@7.19.0` present with 42/112 files, ESM entry `index.mjs` missing) — `dsh --version` still prints fine and boot succeeds, and the breakage only fires when a message triggers pi-ai's dynamic `import('openai')`. **Re-running the install does not fix it**: npm sees the version already present and skips re-extraction.
- **Migration recipe**:
  1. After any interrupted host install, verify three things: `dsh --version` prints; the three bin shims exist in the npm global prefix; and a **real headless round-trip** runs (`dsh headless "只回复两个字:正常"` — this is the smoke that catches half-extracted trees).
  2. If the tree is poisoned, do **not** reinstall over it: rename the package directory aside (`dsh` → `.dsh-corrupt-backup-<date>`), then `npm install -g '@deepseek-ai/dsh@<version>'` fresh (local cache makes this fast), then re-run the three checks.
  3. Fleet declaration flow: per plugin, append the new DSH version to the top compatibility row, bump the patch, rebuild, and release — the manager's gated-update chip reads the ledger, so the row is what turns the chip green.
- **Verification**: fleet dump-config lists every plugin; one headless round-trip per profile; update chips no longer fire after the ledger rows ship.
- **Source**: first-hand fleet upgrade 2026-11-04 (Windows, npm global prefix on a non-system drive); recovery executed and verified live.
