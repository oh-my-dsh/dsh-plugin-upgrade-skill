### DSH-0.1.6-A2-01 · Multi-instance sessions: `sessions.list` loses `current`; the main session moves to `uiSession.current`

- **Type**: breaking
- **Touchpoints**: none (client root services; the sessions list snapshot and the new `uiSession` service)
- **Applies to**: Plugins resolving the current/main session id through `sessions.list.getSnapshot().current` (keyboard helpers, paste/drop handlers, any event-time session resolution outside a slot component)
- **Action level**: required-if-hit
- **Symptoms**: Plugins keep passing their compat guards (the `sessions`/`uiConversation` services still exist) but silently no-op: every current-session read returns `undefined`. First-hand fleet evidence: a composer input-recall plugin lost Ctrl+Up/Down entirely and a paste/drop attachment plugin raised "请先打开一个会话" on every paste after the host upgrade.
- **Migration recipe**: inject the new `uiSession` service (registered by `@deepseek-ai/dsh-client-ui-session`); read `ctx.uiSession.current.getSnapshot()` → `{ key: sessionId, ctx: sessionScope }` where `ctx` is the session-scoped context that replaces `sessions.scope(id)`. Keep the alpha.1 read as a fallback when the service is absent so one build serves both hosts. Slot components (scope `session`) are unaffected — they receive session context through the slot runtime.
- **Verification**: With one session open, the plugin's event-time resolution returns the open session's id; switching sessions changes the id; on alpha.1 hosts the legacy path still resolves.
- **Source**: [dsh-v0.1.6-alpha.2 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.6-alpha.2) · first-hand (2026-09-17 upgrade, fixes shipped: [dsh-input-history v0.1.15](https://github.com/dsh-external/dsh-input-history/commits/v0.1.15), [dsh-paste-input v0.1.27](https://github.com/dsh-external/dsh-paste-input/commits/v0.1.27); the session-scoped shape `{ key, ctx, hooks, keyedHooks, props }` is `createMaterializedBinding` in the alpha.2 client-ui-session bundle)

### DSH-0.1.6-A2-02 · Input-dock standard kit reduced: `useSessions` / `useSessionPendingInteraction` removed

- **Type**: breaking
- **Touchpoints**: none (the `conversation.input.dock` slot's standard props composition)
- **Applies to**: `conversation.input.dock` slot components that destructure global seats beyond the standard kit — first-hand evidence: a resident session-progress strip that called `useSessions(...)` and `useSessionPendingInteraction(...)` unconditionally
- **Action level**: required-if-hit
- **Symptoms**: alpha.2's dock standard kit is only `useConversation` + `useInput` + `inputActions` (per `contract/slots.d.ts` SessionStandardProps). A dock component calling the removed seats throws at render and takes the whole dock subtree down — first-hand evidence: the progress strip vanished entirely after the host upgrade, and a co-tenant dock entry's chips stopped rendering with it.
- **Migration recipe**: make the removed seats optional with graceful degradation — call them through optional chaining and fall back to empty state (`useSessionPendingInteraction?.(...) ?? EMPTY_MAP`), hiding only the affected indicator (subagent pending/running) while the rest of the component renders. Pending-interaction state now lives in the `uiSession` service's status domain (`PendingInteractionDomain` / `sourceFor(owner)`); re-add full detection through that surface once integrated.
- **Verification**: The dock renders on both hosts; on alpha.2 the strip shows state/todos/tokens and simply omits the subagent indicator; no console throw from the dock subtree.
- **Source**: [dsh-v0.1.6-alpha.2 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.6-alpha.2) · first-hand (2026-09-17 upgrade; [dsh-ui-progress v0.10.2](https://github.com/dsh-external/dsh-ui-progress/commits/v0.10.2) shipped with the optional-seat fix)

### DSH-0.1.6-A2-03 · Plugin Manager runtime toggle/install manages `community-plugins` installs; legacy junction + patch installs are not managed

- **Type**: behavior
- **Touchpoints**: none (host plugin-manager surface; plugin install topology)
- **Applies to**: Plugins installed the legacy way — a repo junction/symlink into `~/.dsh/profiles/<profile>/node_modules` plus a manual `cordis.patch.yml` insert row
- **Action level**: informational
- **Symptoms**: The new plugin-management page's real-time enable/disable and install/uninstall operate on plugins installed into the host's plugin store (`~/.dsh/community-plugins`). Legacy junction-installed plugins keep loading through their patch rows and are invisible to the page's toggles — the real-time switch appears broken even though the plugin works.
- **Migration recipe**: Either reinstall the plugin through the Plugin Manager (it lands in `community-plugins` and becomes fully managed), or keep the patch-file install and accept that enable/disable is done by editing/removing the patch row plus a host restart. Runtime unload still requires the plugin's own dispose paths to be fiber-clean (listener/effect pairs), which the upgrade is a good moment to re-verify.
- **Verification**: On the Plugin Manager page, managed plugins show a working toggle; legacy-installed plugins either appear as installed-but-unmanaged or do not appear, matching the chosen install topology.
- **Source**: [dsh-v0.1.6-alpha.2 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.6-alpha.2) · first-hand (2026-09-17 upgrade: six legacy-installed plugins all loaded and served their bundles while being unmanaged by the new page)

### DSH-0.1.6-A2-04 · npm publish lags the GitHub release; pinned upgrades hit an E404 window

- **Type**: behavior
- **Touchpoints**: none (release engineering; install channel)
- **Applies to**: Anyone upgrading `npm install -g @deepseek-ai/dsh@<version>` within hours of a GitHub pre-release; update automation that pins exact versions
- **Action level**: informational
- **Symptoms**: `dsh-v0.1.6-alpha.2` was published on GitHub releases (tag `ddefc45`) but `npm view @deepseek-ai/dsh@0.1.6-alpha.2` returned E404 for at least the first minutes-to-hours; `dist-tags.alpha` still pointed at 0.1.6-alpha.1. An upgrade attempt in that window fails with "No match found for version".
- **Migration recipe**: Poll `npm view` until the version resolves before killing the running host — never start the stop-host phase against an unpublished version. Fallbacks (build from the git tag) are discouraged: the repository root is a private pnpm monorepo (`@deepseek-ai/dsh-root`), so a git/tree install does not produce the published `@deepseek-ai/dsh` package and hand-built trees violate the formal-install rule.
- **Verification**: `npm view @deepseek-ai/dsh@<version> version` resolves before starting the upgrade; after install, `dsh --version` prints exactly the pinned version.
- **Source**: [dsh-v0.1.6-alpha.2 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.6-alpha.2) · first-hand (2026-09-17: E404 observed through three polls ~7 minutes after the GitHub release; npm alpha tag still `0.1.6-alpha.1`)
