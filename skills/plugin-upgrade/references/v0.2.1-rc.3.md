### DSH-0.2.1-R2-01 · New model + web-capability surfaces: DeepSeek-V4.1-Flash-1017 adapter support; opt-in DeepSeek Search & Fetch APIs in web-search settings

- **Type**: capability
- **Applies to**: profile maintainers selecting models (the adapter list gains DeepSeek-V4.1-Flash-1017), plugin authors shipping web-search or fetch providers (a native opt-in provider now shares the same settings page), any plugin that reads the model directory for display
- **Touchpoints**: #2 (model directory contents change), #5 (web search/fetch provider selection in settings)
- **Action level**: informational
- **Symptoms**:
  - The DeepSeek adapter offers V4.1-Flash-1017; existing model selections are untouched.
  - Web search settings gain an opt-in DeepSeek Search/Fetch toggle; when off (default), behavior is byte-identical to rc.1. Plugins providing their own search/fetch providers coexist — the native provider is one more selectable row, not a replacement.
- **Migration recipe**:
  1. Nothing mandatory. If a plugin hard-fails on unknown model ids in the directory (rather than ignoring them), treat that as the plugin's bug — the directory is an open set.
  2. Search-provider plugins that want top billing in the same settings page should verify their display metadata (name/description) reads well next to the native row.
- **Verification**: with the toggle off, run a session that exercised search in rc.1 and diff the tool calls; enable the toggle and confirm the native provider appears as a choice without removing installed providers.
- **Source**: [dsh-v0.2.1-rc.2 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.1-rc.2) ("适配 DeepSeek-V4.1-Flash-1017 上线", "适配 DeepSeek Search 与 Fetch API，可在网页搜索设置中开启").
- **Field note** (first-hand, 2026-10-24): the aggregator benchmark rounds ran V4.1-Flash-1017 through a custom provider endpoint before this adapter existed; the native adapter removes the custom-provider requirement for that model but changes nothing about how in-session subagents address models by name.

### DSH-0.2.1-R2-02 · In-app plugin discovery 「更多」 menus across the left sidebar, conversation views, and right sidebar

- **Type**: capability
- **Applies to**: every published plugin — the menus surface browsing and creation entries where users actually are; marketplace/publisher plugins gain in-app visibility without code changes
- **Touchpoints**: #0 (install surface — discovery now happens in-app, not only via CLI/docs), #5 (plugin creation entry parity with the agent flow)
- **Action level**: optional
- **Symptoms**:
  - New 「更多」 menu entries appear on the left sidebar, conversation views, and the right sidebar, offering plugin browsing and creation.
  - No new plugin-facing API: the menus render existing registry/marketplace metadata. A plugin with sparse or non-localized description text will look sparse in these surfaces too.
- **Migration recipe**:
  1. No code change required. Optional polish: ensure `description` fields and locale metadata (the A1-era locale-aware plugin metadata) are complete — they are what these menus show.
  2. Right-sidebar tab plugins (the A5 tab contract) become reachable from the right-sidebar menu itself; verify the tab title/icon read well out of context.
- **Verification**: open each 「更多」 entry, confirm installed plugins appear with correct names/icons/descriptions, and that a right-sidebar tab plugin opens its tab from the new entry.
- **Source**: [dsh-v0.2.1-rc.3 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.1-rc.3) ("新增左侧栏、会话视图和右侧栏的「更多」菜单，方便浏览和创建插件").

### DSH-0.2.1-R2-03 · New Session reuses the Workspace's blank Session again (reverses DSH-0.2.1-A2-07); API-key adapter model-list sync

- **Type**: behavior
- **Applies to**: client integrations calling `uiWorkspace.startSession(workspaceId)`, `openWorkspace`, or `connectWorkspace`; preset authors who relied on New Session composing the current preset definition ([DSH-0.2.1-A2-07](v0.2.1-alpha.2.md)); profile maintainers using the API-key sign-in mode
- **Touchpoints**: #3 (`uiWorkspace` session-start calls); the model-list sync is host-internal
- **Action level**: required-if-hit
- **Symptoms**:
  - New Session (Web/Desktop) and `uiWorkspace.startSession(workspaceId)` reuse the first unstarted, unarchived blank Session in the Workspace — switched to the default preset — and create a Session only when none exists, so an unsent draft survives a session switch. `startSession` with options, `openWorkspace`, and `connectWorkspace` follow the same rule; a request naming an Agent preset skips blanks listing a different preset.
  - This reverses [DSH-0.2.1-A2-07](v0.2.1-alpha.2.md): a reused blank whose Agent is still loaded keeps the preset composition it was created with, so New Session no longer guarantees the current preset definition.
  - The DeepSeek API-key adapter refreshes its model list through the same mechanism as account login (fewer stale-model-list states after provider-side additions).
  - No service, slot, event, or config-schema rename or removal for plugins in either RC.
- **Migration recipe**:
  1. After changing a preset definition, restart the Host before using New Session (a blank resumed after a restart composes the current definition).
  2. Client integrations that must not take over another preset's blank pass `{ agentPreset }` to `startSession`, `openWorkspace`, or `connectWorkspace`.
- **Verification**: type an unsent draft, switch sessions, use New Session — the same blank opens with the draft. With API-key sign-in, force a model-list refresh and confirm new provider models appear.
- **Source**: [new-session-blank-reuse guide](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.3/docs/upgrade-guide/v0.2.1-rc.2/new-session-blank-reuse/guide.md) at `dsh-v0.2.1-rc.3`; [dsh-v0.2.1-rc.3 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.1-rc.3) ("修复切换会话后，点击「新会话」找不回未发送草稿的问题", "DeepSeek API Key 适配器的模型列表更新方式与账号登录模式保持一致").
- **Field note** (first-hand, 2026-10-24): six-plugin web fleet crossed rc.1 → rc.3 zero-adaptation — `--dump-config` exit 0, better-sidebar API answering structured JSON at its route, no re-releases needed. **Ops lesson worth recording**: the crossing tripped over an npm *global-prefix split* — `npm config prefix` pointed at `E:\npm-global` while PATH resolved `dsh` from the nvm dir (`C:\nvm4w\nodejs`, Machine scope), so the fresh install landed where PATH never looked and `dsh --version` kept reporting rc.1. Machine-scope PATH entries always win over User-scope ones, so a User-scope npm prefix needs its directory *prepended to Machine PATH* (admin, one `SetEnvironmentVariable` call) before the canonical shim is picked up; only then may the old-prefix copy be uninstalled (order matters — removing it first bricks the launcher). Symmetric symptom signature: `npm ls -g` shows the new version while `(Get-Command dsh).Source` still points elsewhere. The E-drive prefix also decouples global packages from nvm's per-version node directories, surviving `nvm use` switches.
