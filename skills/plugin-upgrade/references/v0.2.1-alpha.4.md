### DSH-0.2.1-A4-01 · Plugin compatibility now prefers a declared `engines.dsh`; undeclared plugins keep the existing rules

- **Type**: behavior
- **Applies to**: plugins that declare (or plan to declare) `engines.dsh` in package.json — the field becomes the preferred compatibility source for third-party plugins; plugins without the field are judged by the pre-existing rules
- **Touchpoints**: #0 (packaging — package.json fields)
- **Action level**: required-if-hit
- **Symptoms**:
  - With `engines.dsh` declared, version gating follows that range: a host version outside the declared range is rejected (or flagged) even when the previous rules would have accepted it, and vice versa.
  - Without the field, nothing changes.
- **Migration recipe**:
  1. Inventory whether the plugin declares `engines.dsh` (a fleet-wide grep is enough).
  2. If declared: verify the range covers every DSH version the plugin actually supports, and only those. The gate evaluates ranges with `includePrerelease`, so plain floors such as `>=0.2.0` or `^0.2.0` **do** admit `0.2.1-alpha.4`; the easier mistake is over-admission — an upper bound such as `<0.2.1` still admits every `0.2.1-alpha.N` prerelease. Tighten, widen or drop the field rather than silently excluding supported hosts or admitting unsupported ones.
  3. If not declared: decide deliberately. Keeping the field absent preserves the existing gating (for example a plugin whose compatibility surface is tracked in its own compatibility manifest with exact-version matching may prefer not to declare).
- **Verification**: install the plugin on the oldest and newest supported DSH hosts and confirm the gate accepts both; a deliberately out-of-range host is refused with the engines-based reason.
- **Source**: [dsh-v0.2.1-alpha.4 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.1-alpha.4) ("其他变更" section); the gate is [`packages/boot/app-boot/src/plugin-compatibility.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-alpha.4/packages/boot/app-boot/src/plugin-compatibility.ts) at `dsh-v0.2.1-alpha.4` (line 52: `semver.satisfies(runtimeVersion, range, { includePrerelease: true })`; `engines.dsh` read first, line 56).
- **Field note** (first-hand, 2026-10-16): a six-plugin web fleet crossed to `0.2.1-alpha.4` with zero adaptation — none of the six declares `engines.dsh`, so the existing rules apply unchanged; `--dump-config` loads every row with zero errors and the host keeps `webStartup` (the A2-11 resolution pattern stays valid). Declaration-only re-releases: dsh-ui-whale `v0.3.29`, dsh-file-trace `v0.3.31`, dsh-paste-input `v0.2.12`, dsh-input-history `v0.1.25`, dsh-ui-progress `v0.11.6`, dsh-minigames `v0.3.30` (tags on all three mirrors; `compatibility.json` gains the `0.2.1-alpha.4` entry each). The fleet deliberately leaves `engines.dsh` undeclared: its compatibility manifest tracks exact supported DSH versions for the update chip, and a semver range would either over-admit or under-admit prerelease edges.

### DSH-0.2.1-A4-02 · Custom plugin index sources: discovery and install from user-configured indexes

- **Type**: capability
- **Applies to**: users and plugin distributors — plugins can now be discovered and installed from custom plugin index sources configured in the UI, beyond the default registry flow
- **Touchpoints**: #0 (install/distribution channel)
- **Action level**: informational
- **Symptoms**:
  - A new installation channel: index sources feed the plugin discovery UI; installing still lands in the profile's dependencies and `dsh.profile.bundles` (the A2-era `dsh.bundle.patch` self-registration contract is unchanged).
- **Migration recipe**: none for plugin code; distributors who want index-based discovery publish to an index the user configures. The community-facing caveat from earlier edges still holds for the Add-plugin dialog: it accepts registry names, local paths, and now configured indexes — pnpm alias specs (`name@github:owner/repo#tag`) remain CLI-only.
- **Verification**: configure a custom index and install a known plugin through discovery; confirm the bundle registers and mounts as before.
- **Source**: [dsh-v0.2.1-alpha.4 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.1-alpha.4) ("新增功能" section).

### DSH-0.2.1-A4-03 · Capability round-up: per-model reasoning levels in the UI, command-input integrity, Office delivery polish

- **Type**: capability
- **Applies to**: users of custom model APIs (per-model reasoning levels configured in the UI), the composer (command/argument boundary editing), Office document delivery, Developer Tools, and Linux hosts (faster command launch, older systemd compatibility, failed-command status)
- **Touchpoints**: none (product/user surface; no plugin adaptation)
- **Action level**: informational
- **Symptoms**:
  - New abilities, nothing breaks: reasoning levels for individual custom API models move from hand-edited config into the UI; command-and-argument spans select, delete, and restore as a unit across undo and reloads; Office replies no longer reference deleted preview images or run redundant post-export tool checks; the Developer Tools panel opens after enabling without a reload; Linux command launch drops repeated pre-checks (older systemd included); failed commands report useful status.
- **Migration recipe**: none; profiles that previously hand-configured reasoning levels per model can migrate those settings into the UI at their own pace.
- **Verification**: set a reasoning level for one custom model in the UI and confirm the next request uses it.
- **Source**: [dsh-v0.2.1-alpha.4 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.1-alpha.4).
