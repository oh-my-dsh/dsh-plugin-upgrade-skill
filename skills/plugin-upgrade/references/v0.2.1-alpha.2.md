### DSH-0.2.1-A2-01 · Tool presentation `both` mode is removed — only `native` and `ptc` are accepted

- **Type**: breaking
- **Applies to**: profiles and overlays that set `mode: both` on `@deepseek-ai/dsh-tools` / `@deepseek-ai/dsh-agent-tool-presentation`, deployments using `DSH_TOOLS_MODE=both`, and plugins calling `ctx.tools.presentAs('both')`
- **Touchpoints**: #0 (configuration inventory — `mode` keys, `DSH_TOOLS_MODE` env), #5 (tool registration — `presentAs` calls)
- **Action level**: required-if-hit
- **Symptoms**:
  - The `mode` schema is `z.union(['native', 'ptc'])` — a `both` value is rejected at config load.
  - `DSH_TOOLS_MODE=both` fails through the profile patch that feeds the tools config; `ctx.tools.presentAs('both')` throws.
  - Different presets in one app may still pick different modes.
- **Migration recipe**:
  1. Replace `mode: both` with `native` (direct tool calls) or `ptc` (programs call tools through the generated SDK inside `run_code`) in `cordis.yml`, profile `cordis.patch.yml`, and overlays.
  2. Update `DSH_TOOLS_MODE` likewise; per-preset choice moves to that preset's `@deepseek-ai/dsh-agent-tool-presentation` row.
  3. In PTC programs, keep tool calls inside `run_code`; do not emit SDK function names as direct model tool calls.
- **Verification**: start the affected profile and confirm the config loads; native requests expose the approved direct tools, PTC requests expose `run_code` with its SDK instructions.
- **Source**: [tool-presentation-mode guide](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-alpha.2/docs/upgrade-guide/v0.2.1-alpha.1/tool-presentation-mode/guide.md) at `dsh-v0.2.1-alpha.2`; schema diff in `packages/core/tools/src/index.ts` (the `'both'` union member is removed).
- **Field note** (first-hand, 2026-10-11; corrected 2026-10-13): a six-plugin web fleet crossed to `0.2.1-alpha.2` with zero runtime adaptation — `dsh --profile web --dump-config` loads every plugin row with the host startup compatibility precheck reporting zero errors and zero silent disables, the host boots and listens, and a manual walkthrough passed. None of the fleet uses `mode: both` (the fleet's profiles pin `native`/default), so card A2-01 did not fire. The six three-mirror plugins re-released declaration-only versions on this edge — dsh-paste-input `v0.2.9`, dsh-file-trace `v0.3.27`, dsh-input-history `v0.1.22`, dsh-ui-progress `v0.11.3`, dsh-ui-whale `v0.3.26`, dsh-minigames `v0.3.28` (tags pushed to all three mirrors; `compatibility.json` gains the `0.2.1-alpha.2` entry each). **Correction — dsh-better-sidebar did NOT cross**: it stalls forever as `pending (waiting for service: webRuntime)` because this host line removed the `webRuntime` service (see A2-11); the row loads clean in `--dump-config` (config-level check passes) yet no host routes mount, so the browser-cached client falls through to the static handler and every `/sidebar/api` call returns HTTP 405. `--dump-config` alone is therefore insufficient evidence of a working crossing; a runtime probe (route status or the startup "waiting for services" warning) is required. A local hot-patch renaming the inject to `webStartup` restores activation (verified on a side port).

### DSH-0.2.1-A2-02 · Subagent delegation returns a managed activation; background keys and the in-process driver package are gone

- **Type**: breaking
- **Applies to**: plugins and profiles configuring `@deepseek-ai/dsh-tool-subagent` (`backgroundMode`, `enableRunInBackground`), models passing `run_in_background`, result readers expecting `{ kind: 'foreground' }` / `{ kind: 'background', jobId }`, compositions inserting the removed `@deepseek-ai/dsh-subagent-in-process-driver` row, and custom SDK runtimes
- **Touchpoints**: #0 (tool-subagent config keys), #2 (completion notifications replace job polling), #3 (the deleted in-process-driver service row)
- **Action level**: required-if-hit
- **Symptoms**:
  - Every delegation returns `{ kind: 'activation', subagentId }` once the child agent is admitted; the final answer arrives through parent-completion notifications.
  - Foreground and `{ kind: 'background', jobId }` results are removed; subagents are no longer collected or stopped via `job_output`/`job_kill`.
  - The published `dsh-subagent-in-process-driver` package is deleted; local providers supply creation input via `prepareContinuable()` and the subagent service owns execution. Spawn/Fork children accept follow-up messages; external providers are one-shot.
- **Migration recipe**:
  1. Delete `backgroundMode`/`enableRunInBackground` from the `tool-subagent` config.
  2. Read `subagentId` from the activation result and wait for the recorded completion notification instead of polling jobs.
  3. Remove any `dsh-subagent-in-process-driver` rows; custom SDK runtimes must implement `session/wait`.
- **Verification**: run a delegation on the upgraded profile, confirm the tool returns the child id immediately and the settled notification carries the final answer.
- **Source**: [subagent-activations guide](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-alpha.2/docs/upgrade-guide/v0.2.1-alpha.1/subagent-activations/guide.md); deletions `packages/subagent/subagent-in-process-driver/**` and `packages/subagent/subagent/src/{inbox,continuation,continuation-activation,run-settlement}.ts` in the [alpha.1…alpha.2 comparison](https://github.com/deepseek-ai/deepseek-harness/compare/dsh-v0.2.1-alpha.1...dsh-v0.2.1-alpha.2).

### DSH-0.2.1-A2-03 · Agent Teams deliver messages directly to the target inbox; queued history is never dispatched

- **Type**: breaking
- **Applies to**: users of experimental `@deepseek-ai/dsh-experimental-agent-team` — config setting `maxPendingMessagesPerMember`, and callers reading `send_message` message ids or `accepted`/`queued` status
- **Touchpoints**: #0 (`maxPendingMessagesPerMember` config key), #2 (team message events — queued/delivered records become read-only history)
- **Action level**: required-if-hit
- **Symptoms**:
  - Messages go straight to the target agent inbox; the separate team mailbox, automatic retries, and resend deduplication are gone (`packages/experimental/agent-team/src/mailbox.ts` deleted).
  - `send_message` returns only `{ "sent": true }` — no message id, no `accepted`/`queued`.
  - Queued `team/message/queued` history stays readable but pre-upgrade undelivered messages will never dispatch. `maxPendingMessagesPerMember` is removed; `maxMessageBytes` remains.
- **Migration recipe**:
  1. Before upgrading, let pending messages finish delivering; afterwards explicitly resend anything still needed (check the target history first to avoid duplicates).
  2. Drop `maxPendingMessagesPerMember` from the agent-team row.
  3. Update result readers to `sent` and handle send errors explicitly — success does not mean the target acted. `ctx.agentTeams.sendMessage()` still returns `messageId`.
- **Verification**: on a Team-enabled profile, send a member message and confirm the tool result is `{ "sent": true }` and the target receives it.
- **Source**: [team-direct-inbox guide](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-alpha.2/docs/upgrade-guide/v0.2.1-alpha.1/team-direct-inbox/guide.md); deletion `packages/experimental/agent-team/src/mailbox.ts` in the comparison above.

### DSH-0.2.1-A2-04 · `agent-instructions` drops its `dshHome` config key — instruction loading resolves `$DSH_HOME`/`~/.dsh` only

- **Type**: breaking
- **Applies to**: `cordis.yml`, profile patches, and `--patch` overlays that set `dshHome` on the `agent-instructions` row
- **Touchpoints**: #0 (the `dshHome` config key)
- **Action level**: required-if-hit
- **Symptoms**:
  - The loader resolves the harness home through `@deepseek-ai/dsh-home-paths` `resolveDshHome()` like every other consumer: `$DSH_HOME` when set and non-blank, else `~/.dsh` (tilde expanded).
  - A leftover `dshHome` key has no effect: the row keeps it as a no-op extra and instruction loading follows the process home. Other providers (`dsh-skill-filesystem`, `dsh-shell-env`) keep their own home fields.
  - Global instructions now also load `AGENTS.md` from the shared agents directory; `DSH_AGENTS_HOME` selects that directory.
- **Migration recipe**:
  1. Delete `dshHome` from the `agent-instructions` row in `cordis.yml`, `$DSH_HOME/cordis.patch.yml`, profile patches, and overlays.
  2. If the override pointed at a non-default home, export `DSH_HOME` process-wide so all consumers read the same home.
- **Verification**: `dsh --profile <name> --dump-config` shows the row; a fresh session's first request logs `Instructions from: $DSH_HOME/AGENTS.md` (or `~/.dsh/AGENTS.md`) when the file exists.
- **Source**: [instruction-home-override guide](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-alpha.2/docs/upgrade-guide/v0.2.1-alpha.1/instruction-home-override/guide.md); release notes "全局指令支持读取共享 agents 目录中的 AGENTS.md，可通过 DSH_AGENTS_HOME 指定目录".

### DSH-0.2.1-A2-05 · Python PTC compositions must provide `sandbox` and `sandboxPolicy` services

- **Type**: breaking
- **Applies to**: custom compositions selecting `@deepseek-ai/dsh-experimental-ptc-runtime-python` (published profiles keep the Node runtime and are unaffected)
- **Touchpoints**: #0 (missing service rows fail at load), #3 (sandbox/sandboxPolicy service composition)
- **Action level**: required-if-hit
- **Symptoms**:
  - Direct Python file operations are constrained by the shared file policy; the provider applies it per program and reports it via `PtcRunResult.sandbox`.
  - When constraints cannot be established, restricted runs fail with `sandbox-unavailable` — distinct from a policy rejection.
  - Python remains local macOS/Linux only; resource budgets unchanged, per-call timeout overrides still unsupported.
- **Migration recipe**:
  1. Mount `@deepseek-ai/dsh-sandbox-local` and `@deepseek-ai/dsh-sandbox-policy` (plus its `@deepseek-ai/dsh-session-projection` dependency).
  2. Set the shared `sandbox-policy` row's `mode`/`workspaceRoot` for agent-less calls (default `read-only`; `workspace-write` allows workspace writes). Do not add Python-specific sandbox settings.
  3. Direct service callers use `runtime.run(runtime.resolve(request))`; model-facing `run_code` escalates per-call through the existing approval flow.
- **Verification**: under `workspace-write` a program writes inside the workspace and fails outside; `result.sandbox.mode`/`enforcement` report the applied policy.
- **Source**: [python-ptc-sandbox guide](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-alpha.2/docs/upgrade-guide/v0.2.1-alpha.1/python-ptc-sandbox/guide.md).

### DSH-0.2.1-A2-06 · `dsh plugin` reads `--profile` only before the forwarded pnpm arguments and gains its own help

- **Type**: behavior
- **Applies to**: scripts and documentation invoking `dsh plugin` with `--profile` after the pnpm command (e.g. `dsh plugin add <pkg> --profile <name>`), or relying on `-h`/`--help` forwarding
- **Touchpoints**: none (CLI surface — pre-flight §0 install scripts)
- **Action level**: required-if-hit
- **Symptoms**:
  - `--profile` is parsed only before the first unrecognized token; everything from the pnpm command onward passes to pnpm verbatim, including `-h`, `--help`, and `--profile`.
  - `dsh plugin --help` prints its own usage (`Usage: dsh plugin [options] [args...]`) and exits 0; scripts that placed `--profile` after the pnpm command fail with `required option '--profile <name>' not specified`.
- **Migration recipe**:
  1. Move `--profile <name>` in front: `dsh plugin --profile <name> add <pkg>`.
  2. Ask for a pnpm command's help with the option after that command (`dsh plugin --profile <name> add --help`), or forward `help`.
- **Verification**: `dsh plugin --help` prints its own usage; the reordered install command reaches pnpm.
- **Source**: [plugin-option-placement guide](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-alpha.2/docs/upgrade-guide/v0.2.1-alpha.1/plugin-option-placement/guide.md).

### DSH-0.2.1-A2-07 · New sessions always create a fresh Session and Agent from the current preset definition

- **Type**: behavior
- **Applies to**: Web/Desktop "new session" flows and clients calling `uiWorkspace.startSession(workspaceId)`; anything relying on new sessions reusing a pre-existing empty Session from the workspace
- **Touchpoints**: #3 (`uiWorkspace.startSession` Remote semantics)
- **Action level**: informational
- **Symptoms**:
  - New sessions are created from the current preset definition instead of reusing an existing empty Session that may carry an older composition.
  - Reconnects via `openWorkspace`/`connectWorkspace` still reuse qualifying empty sessions; draft-preparation options keep their reuse rules. Existing agents keep their composition; globally optional tools refresh on their next request after a bundle switch.
  - **Reversed at `dsh-v0.2.1-rc.3`** by [DSH-0.2.1-R2-03](v0.2.1-rc.3.md): New Session reuses the Workspace's blank Session again and no longer guarantees the current preset definition. Deployments past rc.3 follow R2-03.
- **Migration recipe**:
  1. To get agents on an updated preset definition, create a new session; keep using the existing session to preserve the old composition.
  2. Reconnecting integrations keep using `openWorkspace`/`connectWorkspace`.
- **Verification**: change a preset, start a new session, confirm the agent's first request reflects the new definition.
- **Source**: [new-session-generations guide](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-alpha.2/docs/upgrade-guide/v0.2.1-alpha.1/new-session-generations/guide.md).

### DSH-0.2.1-A2-08 · Native subagent bundles (Claude Code, Codex) contribute Host-global delegation tools visible to every preset

- **Type**: capability
- **Applies to**: users of `@deepseek-ai/dsh-subagent-claude-code` and `@deepseek-ai/dsh-subagent-codex`, and presets that registered same-named delegation tools themselves
- **Touchpoints**: #5 (Host-global tool registration under `tool-subagent-claude-code` / `tool-subagent-codex`)
- **Action level**: informational

### DSH-0.2.1-A2-09 · `working_directory` tool ships; the `{{cwd}}` prompt variable is removed and subagent `cwd` config keys are retired

- **Type**: behavior
- **Applies to**: prompt templates (persona/preset suffixes) referencing `{{cwd}}`, configs of `@deepseek-ai/dsh-subagent-acp` / `@deepseek-ai/dsh-subagent-dsh-sdk` with a `cwd` key, and SDK consumers needing to read or change the session working directory
- **Touchpoints**: #0 (`{{cwd}}` in prompt text, subagent `cwd` config keys), #5 (new `working_directory` tool)
- **Action level**: required-if-cwd-variable-used
- **Symptoms**:
  - New packages `@deepseek-ai/dsh-working-directory` (service) and `@deepseek-ai/dsh-tool-working-directory` (tool) provide the session's current execution directory, persisted separately from `Session.header.cwd`; TypeScript and Python SDKs gain read/switch APIs.
  - New subagents take an explicit `cwd` from the start request, else capture the parent's current directory; switching directories changes neither the original project nor write permissions.
  - **Removed at this tag**: the guide (written for alpha.1) announced the removal for the next release, and `dsh-v0.2.1-alpha.2` already registers only `provider` and `model` prompt variables (`git grep "variable('cwd'" dsh-v0.2.1-alpha.2 -- packages/core/agent-loop/src/index.ts` returns nothing; it hits at `dsh-v0.2.1-alpha.1`). Strict interpolation throws `unknown prompt variable "{{cwd}}"`, so a template retaining `{{cwd}}` fails at render and the session never starts — see the [troubleshooting row](troubleshooting.md).
  - `output.presentationMeta` now also runs for successful nested PTC calls — projection authors must not throw (an exception fails that nested call as `ToolOutputError`); canonical values the program reads are unchanged.
- **Migration recipe**:
  1. Remove `{{cwd}}` references from `personaSuffix`/preset `suffix` text now (omit or clear the field when it empties); the working-directory service supplies directory context.
  2. Drop `cwd` keys from subagent provider config.
  3. Use the new SDK APIs for directory reads/changes instead of prompt text.
- **Verification**: grep profiles and presets for `{{cwd}}`; start a session and exercise the `working_directory` tool read/switch.
- **Source**: [working-directory guide](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-alpha.2/docs/upgrade-guide/v0.2.1-alpha.1/working-directory/guide.md); new directories `packages/session/working-directory/` and `packages/session/tool-working-directory/` in the comparison above.

### DSH-0.2.1-A2-11 · The Web profile drops the `webRuntime` service — injects stall pending; `webStartup` carries the trusted hosts

- **Type**: breaking
- **Applies to**: web-profile plugins and overlays that declare `inject: [webRuntime]` or read `ctx.webRuntime.trustedHosts` / `ctx.webRuntime.lanAddresses` (browser-trust fences are the common consumer), and `web-runtime` rows carrying `trustedHosts` config
- **Touchpoints**: #0 (`web-runtime` row config), #3 (service injection)
- **Action level**: required-if-hit
- **Symptoms**:
  - The Web profile no longer provides the `webRuntime` service; a plugin injecting it stalls forever as `pending (waiting for service: webRuntime)` — the row still loads clean in `--dump-config`, so config-level checks do not reveal it (first-hand: dsh-better-sidebar `0.24.x/0.25.0` never activates on this host line; its routes stay unmounted and the browser-cached client receives HTTP 405 from the static fallback on every `/sidebar/api` call).
  - The `web-startup` row provides the single `webStartup` service carrying the `--trusted-host` authorities; `ctx.webRuntime.lanAddresses` is gone.
  - Expressions reading `ctx.webRuntime.trustedHosts` fail to evaluate, which can keep the required Connection from starting.
  - Listen hosts must now be a concrete local IPv4/IPv6 literal — `host: 0.0.0.0`, `--host ::`, and other unspecified addresses are rejected at load (binding all interfaces would expose the port).
- **Migration recipe**:
  1. Replace `inject: [webRuntime]` with `inject: [webStartup]` and `ctx.webRuntime.trustedHosts` with `ctx.webStartup.trustedHosts`; drop `ctx.webRuntime.lanAddresses` reads.
  2. Rewrite the `connection` overlay onto `webStartup`, restating the whole row `config` (patches replace config wholesale).
  3. Replace wildcard listen hosts with a concrete interface address.
- **Verification**: start with `--no-open` and require the `dsh web:` URL line plus zero `waiting for service` warnings; probe one plugin route (a mounted fence answers 401/403/4xx, the static fallback answers 404/405).
- **Source**: [web-listener-trust-config guide](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-alpha.2/docs/upgrade-guide/v0.2.1-alpha.1/web-listener-trust-config/guide.md); the `WEB_RUNTIME_SERVICE` constant present in `packages/bundle/web-app/src/index.ts` at `dsh-v0.2.1-alpha.1` is gone at `dsh-v0.2.1-alpha.2`.
- **Field note** (first-hand, 2026-10-13): hot-patching the installed dsh-better-sidebar `0.24.1` (inject entry plus the one `ctx.webRuntime.trustedHosts` read renamed to `webStartup`) restores full activation on `0.2.1-alpha.2`, verified on a side port — startup warning gone, `/sidebar/api` reaches the fence instead of the static 405.
