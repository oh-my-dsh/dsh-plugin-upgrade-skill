### DSH-0.2.1-A3-01 · The Azure provider is renamed `azure` — `azure-openai-responses` provider configs must migrate

- **Type**: breaking
- **Applies to**: profiles and overlays naming the provider `azure-openai-responses` in model/credential configuration, and any tooling or docs pinning that spelling
- **Touchpoints**: #0 (configuration inventory — provider name keys)
- **Action level**: required-if-hit
- **Symptoms**:
  - A provider configured under the old name no longer resolves after the upgrade; model requests fail with an unknown-provider error.
  - The release notes state the migration plainly: "Azure 提供方名称统一为 azure，使用旧名称 azure-openai-responses 的提供方配置需迁移".
- **Migration recipe**:
  1. Search the profile tree for `azure-openai-responses` (cordis.yml, cordis.patch.yml, overlays, saved credentials).
  2. Rename the provider to `azure`; no other field changes.
  3. Restart the app and send one test request through the Azure provider.
- **Verification**: the model list shows the Azure models and a one-shot request succeeds; no unknown-provider diagnostics at boot.
- **Source**: [dsh-v0.2.1-alpha.3 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.1-alpha.3) ("其他变更" section).

### DSH-0.2.1-A3-02 · API-key resolution priority changes: Web/Desktop read saved credentials first, headless reads env first

- **Type**: behavior
- **Applies to**: deployments that rely on both a saved credential store and `DEEPSEEK_API_KEY`/`.env` simultaneously — especially CI or scripted headless runs on machines that also run the Web app signed in
- **Touchpoints**: #0 (credential sources in the config inventory)
- **Action level**: conditional
- **Symptoms**:
  - Web/Desktop: requests now use the saved account credential even when a different key sits in the environment.
  - Headless: the opposite — env vars and `.env` win, and the saved store is not read.
  - The model-settings UI additionally clarifies the credential source and supports revealing a typed API key.
- **Migration recipe**:
  1. Inventory which credential each surface should use; where the env key and the saved store disagree, decide the winner explicitly.
  2. For headless jobs that must use the saved store, pass the credential explicitly or pre-export the key.
  3. For Web/Desktop where the env key should win, remove/rotate the saved credential instead.
- **Verification**: one Web request and one headless run each log the expected credential source (the model-settings pane names it).
- **Source**: [dsh-v0.2.1-alpha.3 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.1-alpha.3) ("其他变更" section).

### DSH-0.2.1-A3-03 · Plugin updates hot-apply — stale-code-after-reinstall is fixed; replaceable plugins reload without a host restart

- **Type**: fix
- **Applies to**: every profile that updates or reinstalls plugins at runtime (`dsh plugin --profile ... add/update`); release flows that previously instructed a host restart after every plugin bump
- **Touchpoints**: #0 (install/update step of the upgrade recipe), #5 (plugin replacement lifecycle)
- **Action level**: optional
- **Symptoms**:
  - Before this edge, a reinstalled plugin kept running its old code until the host restarted; now, with hot reload enabled, replaceable plugins take effect immediately, and non-replaceable changes prompt a restart instead of silently persisting stale code.
- **Migration recipe**:
  1. Nothing to change in plugin code; the lifecycle is host-driven.
  2. Update release docs/runbooks: after `dsh plugin add`/reinstall, verify the running version in-place (e.g. the plugin's own version chip or a route it serves) before recommending a restart.
  3. Treat an explicit restart prompt as authoritative — a change the host says it cannot hot-reload still needs one.
- **Verification**: bump a plugin in a running profile and confirm the served bundle/version changes without a host restart (or that the host prompts for one).
- **Source**: [dsh-v0.2.1-alpha.3 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.1-alpha.3) ("问题修复" section, stale plugin code fix).
- **Field note** (first-hand, 2026-10-14): a six-plugin web fleet crossed to `0.2.1-alpha.3` with zero adaptation — `dsh --profile web --dump-config` loads every row with zero errors; read-only runtime probes against the live host show dsh-file-trace's mermaid/katex chunk routes answering 200 and the (locally hot-patched) dsh-better-sidebar fence live, so `webStartup`-resolved activation carries over from alpha.2. Declaration-only re-releases: dsh-ui-whale `v0.3.28`, dsh-file-trace `v0.3.30`, dsh-paste-input `v0.2.11`, dsh-input-history `v0.1.24`, dsh-ui-progress `v0.11.5`, dsh-minigames `v0.3.29` (tags on all three mirrors; `compatibility.json` gains the `0.2.1-alpha.3` entry each). One operational wrinkle observed while crossing: a launch racing the previous instance died with `EADDRINUSE` and a "2 required plugins did not activate" diagnostic whose plugin list was purely the port-conflict fallout — when a startup diagnostic names many plugins at once, check the listener table before blaming the plugins.

### DSH-0.2.1-A3-04 · `--from-default-profile` on an existing custom config replaces it wholesale — plugins and settings included

- **Type**: behavior
- **Applies to**: scripts and runbooks that run `dsh --from-default-profile` against a named config that already exists, expecting a merge
- **Touchpoints**: #0 (profile bootstrap commands in the recipe)
- **Action level**: required-if-hit
- **Symptoms**:
  - Rebuilding an existing custom config with `--from-default-profile` now replaces that config's plugins and settings rather than merging; local customizations are gone from the rebuilt config.
- **Migration recipe**:
  1. Before running the rebuild against an existing config, export/preserve any local rows (plugin list, settings) you need.
  2. Re-apply customizations after the rebuild, or build a fresh config name instead of overwriting.
  3. Pin this behavior in automation: treat `--from-default-profile` as destructive to the target config.
- **Verification**: run the rebuild against a scratch config with a deliberate customization and confirm the expectation (replaced, not merged) matches your runbook.
- **Source**: [dsh-v0.2.1-alpha.3 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.1-alpha.3) ("其他变更" section).

### DSH-0.2.1-A3-05 · Capability round-up: in-browser DeepSeek sign-in, sent-message secret masking, `/compact`, SDK resume

- **Type**: capability
- **Applies to**: Web/Desktop users (sign-in, masking, `/compact`), minimal-mode users (image reads, auto-compaction), and TypeScript/Python SDK consumers (resume)
- **Touchpoints**: none (product/user surface; no plugin adaptation)
- **Action level**: informational
- **Symptoms**:
  - New abilities, nothing breaks: DeepSeek account sign-in over local HTTP; keys/tokens in sent messages are detected and masked by default with an on-demand reveal; minimal mode reads images and auto-compacts long conversations, plus a manual `/compact` command on Web/Desktop; both SDKs gain `resume` to continue a saved session under its original id and working directory.
  - Also in this edge (fixes, no adaptation): conversation-area blank/scroll jumps, session-continuation and DeepSeek-switch history compatibility, macOS workspace directory picker, preset-restore failures, old-Git worktree creation, remote-Web false disconnects and lost preferences, "任务已停止" for interrupted tasks, extra credential fields no longer blocking startup, session-store uninstall flushing.
- **Migration recipe**: none; note the masking behavior when sharing screenshots of conversations (masked by default is the new safe baseline).
- **Verification**: sign in on a local-HTTP Web session, send a message containing a token-shaped string (it masks), and run `/compact` once.
- **Source**: [dsh-v0.2.1-alpha.3 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.1-alpha.3).
