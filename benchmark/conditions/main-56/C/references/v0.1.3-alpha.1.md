### DSH-0.1.3-A1-01 · v0→v1 migrator refuses 0.1.2-alpha.x session logs (`replayState` `kind`)

- **Type**: breaking
- **Applies to**: Host plane. Any deployment upgrading from 0.1.2-alpha.x with real session history to 0.1.3-alpha.1; any plugin/integration that reads session logs across this boundary inherits the same refusal through the persistence layer.
- **Touchpoints**: #2, #4
- **Action level**: required-if-hit
- **Symptoms**: the 0.1.3 Web UI shows
  `Failed to load history: failed to observe session "session-<id>": @deepseek-ai/dsh-session-format-v0-to-v1 refuses this format v0 Session: assistant/chunk 95 chunk replayState has unexpected member "kind"; source v0 artifact remains unchanged (raw log: …)`.
  What looks like "slow loading" before the failure is the migration scan itself (40 s+ for
  a ~16 MB log, no progress or error surfaced while it runs).
- **Migration recipe**: none available yet. Do not hand-edit v0 logs — the migrator is
  fail-closed and leaves the source artifact unchanged, so nothing is corrupted, but the
  session stays blocked. Until an upstream fix or an official rewrite path exists, keep a
  0.1.2-rc.1 installation available for reading old logs (rc.1 loads them natively — it has
  no v0→v1 migrator on this path).
- **Verification**: after an upstream fix lands, open a previously refusing session on
  0.1.3; message and tool-card counts must match the 0.1.2-rc.1 rendering of the same log.
- **Source**: measured 2026-09-05 on the release-tarball build `0.1.3-alpha.1-9523542`; the
  refusal string reproduced on two sessions (15.7 MB / 19 MB logs, refusing at chunks
  ~95/~94) out of a 6-session real-history batch (same writer family, all refused). Full
  evidence chain (build identity, CDP timing, raw refusal strings, three-leg attribution):
  [upstream-0.1.3 adaptation audit, pinned](https://raw.githubusercontent.com/alex04130/dsh-forge/8ab0b148b2382b2a33158039fd10d7625b4e145a/docs/audits/upstream-0.1.3-adaptation-audit.md)
  (§0/§7/§7.5). Official writer coordinates: `@deepseek-ai/dsh-llm-pi-ai` `toPiReplayState()`
  in the installed 0.1.3-alpha.1 tree (`response.kind: "pi-ai"`, `version: 2`) — this
  version is distributed via the release-tarball channel and is not on npm
  (`latest`/`alpha`/`next` = 0.1.2-rc.1/alpha.5/0.1.2-rc.1, registry checked 2026-09-06);
  re-verify against the official tag once it is published.
  Comparison control: the same batch loads natively on 0.1.2-rc.1 (no migration face) and
  in the 0.1.2-alpha.3 writer home.

Root cause (observed shape) — the refused member is written by official core, not plugins.
Three-leg proof, measured 2026-09-05:

1. **Plugin negative scan**: zero hits for `replayState` / `assistant/chunk` writes across
   all local plugin sources (dynamic plugins, profile plugins, community plugins).
2. **Official writer**: the pi-ai adapter `@deepseek-ai/dsh-llm-pi-ai` constructs the
   replay envelope itself in `toPiReplayState()` — `response.kind: "pi-ai"`, `version: 2`
   (installed tree, official package).
3. **Older writer generation layered in the append-only log**: the refused
   `assistant/chunk` events carry
   `replayState: {kind: "pi-ai", version: 1, api: "openai-completions", …}` — `kind` at the
   top level with `version: 1`, emitted by the pre-alpha.4 writer generation and preserved
   verbatim in the append-only log. The 0.1.3 `dsh-session-format-v0-to-v1` migrator
   validates `replayState` against a single-generation schema, so it rejects the layered
   older-generation member and refuses the whole session (fail-closed; the source v0
   artifact stays unchanged — good safety behavior, but the net result is a hard block on
   history).

```json
{"type":"assistant/chunk","seq":95,"data":{"turn":1,"step":1,"chunk":{"type":"finish","reason":{"kind":"tool-calls"},"replayState":{"kind":"pi-ai","version":1,"api":"openai-completions","provider":"…","model":"…","responseModel":"…","responseId":"…","stopReason":"toolUse","blocks":[…]}}}}
```

`replayState.kind` at the top level with `version: 1` marks the older writer generation; the
current official writer nests `kind` inside `response` with `version: 2`.

- **Field note** (2026-09-05, reporting deployment): performance contrast on the same
  15.7 MB session — 0.1.2-alpha.3 opens it in ≈3.0 s (headless CDP measurement); 0.1.3
  spends 40–200 s scanning before refusing, with an undifferentiated "Loading history…"
  state. Expected behavior: accept the writer-family discriminator (or provide a documented
  0.1.2→0.1.3 log rewrite path), and surface per-session migration progress/failure
  promptly instead of an indefinite loading state.

### DSH-0.1.3-A1-02 · cross-version `resume` on 0.1.2-alpha.3 logs reports `cursor behind the last applied entry`

- **Type**: behavior
- **Applies to**: Host plane. Deployments on 0.1.3-alpha.1 resuming a session whose log was
  written by 0.1.2-alpha.3 (fresh log — distinct from the refused-history case in
  DSH-0.1.3-A1-01).
- **Touchpoints**: #2
- **Action level**: required-if-hit
- **Symptoms**: resuming such a session on 0.1.3 reports
  `cursor behind the last applied entry (gateway/internal)`; the resumed turn does not
  start.
- **Migration recipe**: none yet. Do not retry blindly — the error surfaces as a
  `gateway/internal` failure; only retry when the operation is confirmed idempotent. Keep
  the 0.1.2 line available for resuming these sessions until an upstream fix or a
  documented resume-migration path exists.
- **Verification**: after an upstream fix, resume the same session on 0.1.3; the resumed
  turn must append to the log and stream a reply without the cursor error.
- **Source**: measured 2026-09-05 on the same release-tarball build
  `0.1.3-alpha.1-9523542`; single observed case (fresh 0.1.2-alpha.3-written log) — scope
  intentionally narrow, treat as a reproduction record pending wider confirmation.
  Evidence context:
  [upstream-0.1.3 adaptation audit, pinned](https://raw.githubusercontent.com/alex04130/dsh-forge/8ab0b148b2382b2a33158039fd10d7625b4e145a/docs/audits/upstream-0.1.3-adaptation-audit.md).

## Corridor status

- First two cards for the 0.1.2 → 0.1.3 boundary. Both are session-log plane findings from
  one deployment's real-history upgrade trial, not a complete 0.1.3 API sweep; plugin-facing
  API changes for this corridor are not yet curated.
- Both cards are fail-closed reader behaviors acting on official writer output. Plugin
  sources were negatively scanned (zero `replayState` / `assistant/chunk` writes) as part of
  the attribution, so the corridor edge is between official writer generations, not caused
  by third-party plugins.
