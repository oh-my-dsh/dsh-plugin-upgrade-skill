# S类诊断题的LLM评分规则

S11、S13、S14、S16、S17、S18、S19、S20、S21、S22默认使用LLM-as-judge。
任务版本为`4.1.0`，协议为`report-judge-v2`。题面、fixture和原参考答案保持不变；
旧关键词评分及此前不同rubric的LLM结果不能直接与新版分数比较。
主线#212已迁移其中7题；本次补齐S13、S14、S20，并细化全部10题的判分条件。

规则源文件是[diagnosis-rubrics.mjs](../report-judge/diagnosis-rubrics.mjs)，
由[rubrics.mjs](../report-judge/rubrics.mjs)统一注册。
下面是便于审核的中文说明，实际判分使用各题封存的`tests/packet.json`。

## 分数如何计算

- 每题满分100分。每个评分项由模型返回`pass / partial / fail / missing`，
  程序分别计该项权重的100% / 50% / 0% / 0%。模型不能自行决定总分。
- 满分要求结论正确、因果解释成立，并覆盖该项必要内容；只覆盖其中一部分可得半分。
  列关键词、卡号、照抄问题，不能代替诊断。
- 接受中英文、等义表述、不同段落顺序、合理的等价代码和验证方案。
  先后顺序按方案的执行依赖判断，不按词在报告中出现的位置判断。
- 封顶只针对明确采纳的错误结论或最终建议。引用错误示例并予以否定，不触发封顶。
  先写正确方案、最后又明确推翻为错误方案，要按完整报告的最终主张判断。
- 这是只读报告任务，要求提出验证方法，不要求安装、修复或运行产品。
  不能通过声称“已经验证”取得额外分数，也不要求补出材料未提供的内部实现。
- fixture的新增、修改、删除均由封存哈希确定性检查，违规直接0分；缺报告或仅复制题面也为0分。
  API/配置/判分协议失败不产出reward，不能伪装成考生0分或退回关键词评分。

## 材料边界

- S13：peer声明是兼容性主张，不证明作者测试过；不强求复述fixture注释中的范围上界。
- S16：根据本次日志判断自宿主依赖危险，不要求“所有平台的每次全局升级都必然崩溃”。
- S17：接受block callback等价包装，不按变量名、空格或箭头函数排版判分。
- S18：23个差异格与肉眼看到的6像素簇是不同口径；不能将漂移后的帧用作可信基准。
- S19：支持拼接帧的解码器与手工逐帧循环都可用；无效XML不能跳过校验直接进入iframe。
- S21：manifest节录的60与probe的62保持为材料差异；不要求虚构解释。
  允许说明URL受限并分组，而不背出3KB常数。题面未提供fold修复版本，不能将其设为满分条件。
  session-only认领范围解释绝对地址错误，不能解释已打开tab的metadata停滞。
- S22：删除重复insert只能解决本次组合错误，不等于原来的内容读取问题也解决。

## 校准与运行

每题准备12类样例：完整、重排、纯关键词、错误结论、注入指令、虚构引用、
复制题面、历史Oracle、独立中文表述、正确否定、末尾矛盾建议、部分答案。
原始Oracle只保留供比较，不预设满分。完整校准答案单独保存，修正了已发现的
过度概括或遗漏；不改写历史参考答案。

[校准样例](../report-judge/calibration/diagnosis.mjs)的预期区间是待实测的假设，
单元测试只验证样例完整、封存边界、传输和分数聚合，不冒充模型已通过语义校准。
