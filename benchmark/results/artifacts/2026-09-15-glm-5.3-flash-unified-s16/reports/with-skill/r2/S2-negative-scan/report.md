## 2 · Hit → change-card mapping

### Hit 1 — `inject: ["apiProxy"]` + `ctx.apiProxy.llm.providers()` (index.js:3,9) + removed dependency (package.json:17)

- **Covering card: DSH-0.1.2-A1-01** (breaking, required-if-hit, touchpoint #3) — APIProxy removed; alpha.1 deletes the service key `apiProxy` and the package `@deepseek-ai/dsh-host-apiproxy` entirely (the package is also on rollup **R-05**'s list of 5 packages removed rc.2 → alpha.1). On the target, the declared inject can never resolve: the entry sits at `pending (waiting for service: apiProxy)` forever, without an explicit error.
- **Face determination (per A1-01 field note / API-01)**: this is a host-plane consumer, so the migration is **not** the `ctx.remote.*` table — mechanically switching to `inject: ["remote"]` would hang on the host plane (`pending (waiting for service: remote)`). The correct target shape for this plugin is to inject the owning domain service directly: `export const inject = ['llm']` and `ctx.llm.listProviders()` (plus `.listConfigurableProviders()` — the old `llm.providers` call was split into two results per the A1-01 ledger row `llm.providers → llm/listProviders + llm/listConfigurableProviders`).
- **Secondary card: DSH-0.1.2-A2-02** (breaking, required-if-hit, touchpoint #3) — once the call becomes a unary Remote/domain call returning `RemoteResult<T>`, the current error handling at `index.js:11-13` (`catch (error) { console.error(...error.message) }`) is the exact "defensive catch" anti-pattern A2-02 warns about: business failures no longer reject — they arrive as `{ ok: false, error }` with namespaced codes (`<domain>/<reason>`, e.g. `gateway/cancelled`, `gateway/internal`). The migrated call site must branch on `result.ok` / `result.error.code` and keep the catch only for local assembly faults; it must not parse `Error.message` or branch on old unprefixed code strings.
- **Cohort-level recipes (not touchpoint hits, but the same files)**: dependency rewrite per **R-01/R-08** — drop `@deepseek-ai/dsh-host-apiproxy` (removed package; the `0.0.1-rc.1` pin is a vanished-registry pin), pin the target cohort explicitly, and beware peer-floor prerelease semantics; pre-migration removed-package inventory per **R-05**; peer floors per the [precision checklist](../../../../../../../../skills/plugin-upgrade/references/precision-checklist.md) — `inject-lint` on the fixture currently returns `verdict: "FIX-REQUIRED"` with `cordisOk: false` (no `@deepseek-ai/cordis` peer at `^4.0.1`; a `-rc` cohort pin survives in `dependencies`). These are dependency/packaging surfaces, not one of the seven classes — which is itself evidence that a seven-class scan alone cannot clear a plugin.

## 4 · Can the zero-hit categories prove compatibility with 0.1.2? — **No.**

**Judgment: the no-hit verdicts are necessary evidence but not sufficient; they cannot conclude compatibility — and in this very plugin they coexist with a hard incompatibility.**

Basis:

1. **The scan is a heuristic by its own definition.** [pre-flight.md](../../../../../../../../skills/plugin-upgrade/references/pre-flight.md) states it verbatim: "This is a heuristic scan, not proof of compatibility. Zero hits across the seven classes only means 'not detected by the current patterns'; you must still check dependencies/configuration and run a build, a real mount, and functional smoke tests." The planner output repeats the same limit, and the card sets are explicitly "curated, not a complete API diff" — absence of a card is not absence of impact (both alpha.1 and alpha.2 card files close with exactly this warning).
2. **This plugin is a live counterexample to "mostly zero hits ≈ compatible".** Six of seven categories are zero-hit, yet the plugin is *definitively incompatible with 0.1.2-alpha.2 as written*: its single #3 hit is a required-if-hit breaking card (DSH-0.1.2-A1-01) whose subject — the `apiProxy` service and the whole `@deepseek-ai/dsh-host-apiproxy` package — was deleted in alpha.1. Mounted as-is on the target, the entry never activates (`pending (waiting for service: apiProxy)`). Zero hits in the other six categories do not dilute a required-if-hit card by even one gram.
3. **Compatibility lives partly outside the seven classes.** The dependency cohort (`@deepseek-ai/dsh-host-apiproxy@0.0.1-rc.1` must be removed; cohort peers floored per the precision checklist — `inject-lint` already reports FIX-REQUIRED on the peer floor), the composition row, the packed-artifact check (API-07), strict-injection semantics (R1-04 lineage), and the `RemoteResult` wire contract (A2-02) are all surfaces a class-scan no-hit says nothing about.
4. **The fixture cannot supply the remaining evidence.** It is a static copy with no lockfile, no git history, and no installable environment — so the exact `from` pin, the R-06 baseline, dependency resolution, and any runtime layer are uncollectable here.

**What is needed before a compatibility conclusion can be drawn** (the mandatory post-migration steps; listed, not executed — this task is scan-only and nothing may modify `fixture/`):

1. Pin the exact `from` cohort against the real repository (lockfile + git SHA; if it predates `dsh-v0.1.1-rc.1`, treat the leading segment as a draft/unsupported gap per the corridor rules — with a plugin this small the net state is still computable, but it must be recorded, not assumed).
2. Collect the R-06 baseline (build/typecheck/tests in the repository's own dependency state) before any migration write, so pre-existing failures are not misattributed.
3. Perform the A1-01/A2-02 migration in a dedicated branch: `inject: ['llm']` + `ctx.llm.listProviders()`/`listConfigurableProviders()` with `result.ok` branching; remove the dead dependency; rewrite cohort pins (R-01/R-08); keep the composition row.
4. Then run the verification ladder:
   - Dependency resolution: full lockfile scan for the old cohort and removed package; `inject-lint` returns OK; no peer warnings (R-08: rewrite the peer floor to the target cohort explicitly).
   - Static: build; typecheck is N/A for this plain-JS plugin (no tsconfig), but if type dependencies are added, `@deepseek-ai/cordis` at `^4.0.1` exactly.
   - Enablement: `dsh --profile <p> --dump-config` on an isolated profile — row `minimal-llm` present, **no** `pending (waiting for service: …)` lines.
   - Runtime: cold boot in an isolated profile (e.g. `verify-runtime.mjs`, which really installs and runs plugin code — per its own docs it must run in a throwaway container for untrusted plugins); prove entry activation, not just a successful install.
   - Behavior: one real provider-list round covering `ok: true` **and** one domain error code; assert the failure path surfaces errors instead of the old swallow-and-log (the A1-30 field-note lesson: a silent catch leaves the feature dead while every smoke stays green).
   - Pack smoke: confirm `cordis.patch.yml` is inside the tarball (API-07).
