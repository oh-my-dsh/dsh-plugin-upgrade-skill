# S16 · The Self-Host Upgrade Trap — Analysis Report

Task: explain the structural failure of an in-session `npm install -g @deepseek-ai/dsh@0.1.2-rc.1`, the broken state it left, the correct repair, the protocol the agent should have followed, and prevention.

Sources: fixture evidence pack (agent-session-log.txt, env-state.txt, repair-notes.md) under E:\deepseek-harness\dsh-plugin-upgrade-skill\benchmark\tasks\S16-self-host-upgrade-trap\environment\fixture (read-only).

## 1. Structural root cause

The failure is structural, not flaky. The agent, its web session, and the pwsh tool worker that executed the npm call all live inside the running dsh host process — `node .../node_modules/@deepseek-ai/dsh/...` — which is itself loaded from the exact npm global tree that the install command was replacing.

Sequence from the log:

- `npm warn cleaning node_modules/@deepseek-ai/dsh` — npm deletes the running package's directory first. On Windows the loaded files cannot always be deleted while mapped, but npm's reify flow removes/replaces package content and the shims well before linking the new version.
- The moment package files or the `dsh`/`dsh.cmd` shims under `%APPDATA%\npm` are removed, the running host process (whose module graph and any spawned children resolve into that tree) loses its footing: the web GUI connection died at 16:41:31, right at `npm info linkStuff`, i.e. during the link/shim-writing phase.
- The pwsh tool worker was a child of that host. When the host died mid-call, the worker was killed with it, so the tool call never returned: the session log records the call but "<no result recorded — the tool call was interrupted after it was recorded, but no result was durably recorded. Its outcome is unknown."

So the agent was simultaneously the upgrader and the upgrade target's runtime. npm's global install is not atomic; it removes the old tree before fully linking the new one, and destroying the old tree kills the process that is supervising the install. By construction the install can never complete under its own supervision.

## 2. The broken state afterwards

From env-state.txt and the log's post-mortem shell:

- The `dsh` command vanished because the command is just the shim trio (`dsh`, `dsh.cmd`, `dsh.ps1`) in `%APPDATA%\npm`. After the interrupted install: `dsh.cmd` and the extensionless `dsh` are MISSING and `dsh.ps1` is stale (points into the old tree). Content presence is irrelevant — the package directory still holds (rc.1) files, but PATH resolution fails before content matters. A half-finished npm reify leaves content without a consistent install: shims not (re)generated, and per the repair notes the directory had additionally been hand-swapped during the user's partial manual repair, making it a NON-STANDARD tree.
- Hand-swapping or patching directories makes it worse because npm global installs are registry-stateful, not just files-on-disk: npm tracks the installed tree (its lockstate/ideal tree) and the shims are generated by the bin-linking step of a formal install. A manually assembled directory (a) never regenerates the missing `dsh`/`dsh.cmd` shims, (b) diverges from what npm believes is installed, so any later npm operation re-breaks or "cleans" it (the log already shows npm "cleaning" a prior manual state), and (c) mixes rc.1 files with leftovers — exactly the "present, partially replaced" state recorded. Repair must go through npm, not the file system.

## 3. The repair actually applied

Per repair-notes.md:

1. Re-run the formal install from the registry: `npm install -g @deepseek-ai/dsh@0.1.2-rc.1` — executed by a different agent CLI outside dsh. This regenerated `dsh`, `dsh.cmd`, `dsh.ps1` and restored a standard tree; `dsh --version` → 0.1.2-rc.1.
2. Aligned the host-source-reference workspace checkout from the alpha.5 tag to `dsh-v0.1.2-rc.1` (no local-modification conflicts).

Why this works where the in-session attempt could not: the repairing process is not the upgrade target. An external CLI runs from its own package tree, so removing/replacing the dsh global tree cannot kill it; npm can therefore run to completion, write the full package, and perform the bin-linking step that recreates the shims. Verification: `dsh --version` reports rc.1, all three shims exist; the notes additionally leave real-machine verification to the user (start `dsh --profile web`, hard-refresh the browser, confirm plugins load — whale/progress etc.) and optional cleanup of `dsh-old-*` backups after confirmation.

## 4. The protocol the agent should have followed

Recognition: the agent must notice that it is executing inside the host process that IS the upgrade target — the GUI session, the tool worker, and the npm global package are one dependency chain. Therefore it must not execute the global install itself at all; any in-session attempt is self-destruction regardless of luck, timeouts, or retries.

Instead, hand the user an external procedure, in this order:

1. Before npm runs — stop the running host: close the dsh web session / exit the `dsh web` host process (and any dsh-sourced terminals or background sessions) so nothing holds files in the global tree. This is the step that makes the install safe; it must precede npm.
2. Then, from an ordinary external shell (PowerShell not spawned by dsh):
   `npm install -g @deepseek-ai/dsh@0.1.2-rc.1`
   A full formal registry install — not a directory swap, not `--no-bin-links`, not copying over the old tree — because the command must regenerate the `dsh`/`dsh.cmd`/`dsh.ps1` shims and leave a standard tree.
3. After: verify `dsh --version` → 0.1.2-rc.1, restart `dsh --profile web`, hard-refresh the browser, confirm plugins load; optionally remove `dsh-old-*` backups once confirmed. If the workspace checkout is used for host-source reference, align it to the `dsh-v0.1.2-rc.1` tag.

Which parts follow from known upgrade rules vs. what is new:

- Known upgrade rules: use a formal `npm install -g <pkg>@<version>` from the registry rather than manual directory surgery; verify with `--version` and restart the host afterwards; align any source-reference checkout to the new tag. These are ordinary version-upgrade discipline.
- New for this incident: the ordering constraint that the dsh host (the agent's own process) must be stopped BEFORE npm runs, and the categorial rule that a dsh-hosted agent must never itself run the global dsh install — it can only hand the procedure to the user, because the preconditions for the install include the agent's own death.

## 5. Prevention

Agent-side guard:

- A pre-execution guard in the shell/subprocess tool path (or a hooks/loop-hygiene plugin) that inspects the command before it runs and refuses — with an explanatory message and the external procedure — any command that (a) invokes npm/pnpm with `-g`/`--global` (or otherwise writes to the global prefix) AND (b) targets `@deepseek-ai/dsh` or `dsh*`, when the session is running inside the dsh host. The refusal message should state the structural reason ("this session runs inside the package being replaced") and emit the hand-off procedure from §4 rather than a bare denial. A softer layer can also warn on any `npm install -g` that touches the running host's own module tree (via `process.execPath`/module paths vs. the npm global prefix).

Post-upgrade checklist for this machine (given the alpha.5→rc.1 findings):

- Confirm all three shims exist and `dsh --version` → 0.1.2-rc.1 (the exact failure mode here was shim loss, not content loss).
- Restart `dsh --profile web`; hard-refresh the browser; confirm plugins load (whale / progress / etc.) — the repair notes explicitly leave this real-machine check to the user.
- No plugin re-migration needed: the alpha.5→rc.1 diff is 252 files, all package.json version bumps, zero API/feature changes — so skip migration work and note that fact rather than re-running migrations speculatively.
- Align the source-reference workspace checkout to the `dsh-v0.1.2-rc.1` tag (done in repair; verify no local-modification conflicts remain).
- Clean up the accumulated `dsh-old-*` backup directories once rc.1 is confirmed working.
- Verify the tree is a standard npm install (no hand-swapped remnants) so future npm operations don't "clean" it back into a broken state.
