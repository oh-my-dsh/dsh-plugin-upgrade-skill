### DSH-0.1.6-A2-01 · Multi-instance Session references: `SessionListState.current` is removed; resolve the main Session through `uiSession.adapter.current`

- **Type**: breaking
- **Touchpoints**: none (client root services: the Session Controller list snapshot and the `uiSession` service from `@deepseek-ai/dsh-client-ui-session`)
- **Applies to**: Plugins resolving the current/main session id through `sessions.list.getSnapshot().current` or `useSessions(s => s.current)` (keyboard helpers, paste/drop handlers, any event-time session resolution outside a slot component)
- **Action level**: required-if-hit
- **Symptoms**: On alpha.1 `SessionListState` carried `current: SessionId | undefined` (`packages/api/session-controller/src/client/sessions/service.ts:74`); on alpha.2 the interface (`:53-67`) has no `current` field, because Session ownership becomes per-source reference counts and "current" now means main-view occupancy — a row whose `retainedBy.mainView` count is positive (architecture note `2026-09-15-client-session-references.md:80`). Plugins keep passing their compat guards (the `sessions`/`uiConversation` services still exist) but silently no-op: every current-session read returns `undefined`. First-hand fleet evidence: a composer input-recall plugin lost Ctrl+Up/Down entirely and a paste/drop attachment plugin raised "请先打开一个会话" on every paste after the host upgrade.
- **Migration recipe**: `uiSession` is not new — it is registered by `@deepseek-ai/dsh-client-ui-session` on both tags (alpha.1 `ui-approval` already injects it) — but its field holding the current binding is private on both (`private currentBinding` on alpha.1, `private readonly current` at `packages/client/ui-session/src/client/index.ts:280` on alpha.2). The public path that works on both hosts is the slot-scope adapter: inject `uiSession` and read `ctx.uiSession.adapter.current.getSnapshot()`, a `StandardSourceBinding` whose `key` is the main Session id (or `undefined` with no Session); when `key` is defined the binding is a `ScopedStandardSourceBinding` that also carries the session-scoped `ctx`. Subscribe through `ctx.uiSession.adapter.current.subscribe(listener)` if the plugin caches the id. On alpha.2 the same fact can also be derived from the catalog as the row with `retainedBy.mainView > 0` in `sessions.list.getSnapshot().byId` (note `:80`, `:152`). Slot components (scope `session`) are unaffected — they receive session context through their Provider.
- **Verification**: With one session open, the plugin's event-time resolution returns the open session's id on both alpha.1 and alpha.2 hosts; switching the main-view session changes the id; with no session open the resolution returns `undefined` rather than throwing.

### DSH-0.1.6-A2-02 · Global standard props: `useSessionPendingInteraction` is replaced by `useSessionStatus` (plus the new `useSessionRetainInfo`); `useSessions` stays

- **Type**: breaking
- **Touchpoints**: none (the `GlobalStandardProps` that `@deepseek-ai/dsh-client-ui-session` merges into every slot's standard props, including `conversation.input.dock`)
- **Applies to**: Slot components that destructure `useSessionPendingInteraction` from their standard props — first-hand evidence: a resident session-progress strip in `conversation.input.dock` that called it unconditionally
- **Action level**: required-if-hit
- **Symptoms**: On alpha.1 `GlobalStandardProps` held `useSessions` and `useSessionPendingInteraction` (`packages/client/ui-session/src/client/index.ts:104-110`). On alpha.2 it holds `useSessions`, `useSessionStatus` and `useSessionRetainInfo` (`:155-160`): `useSessionPendingInteraction` is gone, `useSessions` remains (its snapshot just lacks `current`, see DSH-0.1.6-A2-01). The dock slot itself is unchanged — `'conversation.input.dock': { kind: 'list'; scope: 'session'; owner: InputZone }` and the session kit `useConversation` / `useInput` / `inputActions` are declared the same way on both tags (`packages/client/ui-conversation/src/client/contract/slots.ts`). A component that calls the missing prop throws at render and takes the whole dock subtree down — first-hand evidence: the progress strip vanished entirely after the host upgrade, and a co-tenant dock entry's chips stopped rendering with it.
- **Migration recipe**: Replace the pending-interaction read with the unified status hook: alpha.1 `useSessionPendingInteraction(snapshot => snapshot.get(sessionId))` (a `ReadonlyMap<SessionId, SessionPendingInteraction>`) becomes `useSessionStatus(snapshot => snapshot.get(sessionId)?.pendingInteraction)` on alpha.2, whose `SessionStatus` record also carries `running` and `completionUnread` (`:56-70`; architecture note `2026-09-15-client-session-references.md:92-102` says Workspace status indicators and composer selection moved to `useSessionStatus` for the same reason). To serve both hosts from one build, pick the hook by which prop the host supplies — the set of props is fixed per host, so the branch is stable across renders — and degrade to an empty state when neither is present. `useSessionRetainInfo(sessionId, selector)` / `useSessionRetainInfo(selector)` is the new public way to read reference counts such as `retainedBy.mainView`.
- **Verification**: The dock renders on both hosts with no console throw from the dock subtree; on alpha.2 a pending approval in the session shows up through `useSessionStatus`, and on alpha.1 through `useSessionPendingInteraction`.

### DSH-0.1.6-A2-03 · New Plugin Manager service manages profile bundles and patch-row toggles; link-installed plugins stay outside its bundle management

- **Type**: behavior
- **Touchpoints**: none (host plugin-manager surface; plugin install topology)
- **Applies to**: Plugins installed the legacy way — a repo junction/symlink into the profile's `node_modules` plus a manual `cordis.patch.yml` insert row — and plugin authors deciding how users should install them on alpha.2
- **Action level**: informational
- **Symptoms**: alpha.2 adds `packages/boot/plugin-manager` (absent on alpha.1) behind the Web sidebar's **Plugins** page and the `plugin_manager` tool. Per its README, it manages the current profile's *bundles* and their uniquely addressable rows: a bundle toggle edits the ordered `dsh.profile.bundles` list in the profile directory's `package.json`; install and remove run pnpm in the profile directory (a failed or cancelled install restores `package.json` and `pnpm-lock.yaml`); a plugin-row toggle updates only `disabled` in the last matching override in the profile's `cordis.patch.yml`, or appends one; `listBundles` leaves out an unselected plain dependency; changes apply immediately only with HMR enabled, otherwise at restart. There is no separate plugin store directory — earlier drafts of this card named `~/.dsh/community-plugins`, which does not exist upstream. First-hand observation (2026-09-17, not upstream documentation): six link-installed plugins with hand-written patch insert rows all kept loading and serving their bundles, but the Plugins page did not manage them as bundles, so the real-time toggle appeared not to apply to them even though the plugins worked.
- **Migration recipe**: To be fully managed, ship the plugin as a package that declares a bundle and install it through the Plugins page, the `plugin_manager` tool, or `dsh plugin` — it then lands in the profile's `package.json` / `dsh.profile.bundles` and pnpm lockfile. Or keep the link install and manage it by editing the profile's `cordis.patch.yml` (a `disabled` override on the row) plus an HMR reload or host restart. Runtime unload still requires the plugin's own dispose paths to be fiber-clean (listener/effect pairs), which the upgrade is a good moment to re-verify.
- **Verification**: After installing through the manager, the profile `package.json` lists the bundle under `dsh.profile.bundles` and toggling it in the Plugins page changes that list; toggling a row writes a `disabled` override into the profile `cordis.patch.yml`. A link-installed plugin shows up (or not) according to that model, matching the chosen install topology.

### DSH-0.1.6-A2-04 · npm publish lags the GitHub release; pinned upgrades hit an E404 window

- **Type**: behavior
- **Touchpoints**: none (release engineering; install channel)
- **Applies to**: Anyone upgrading `npm install -g @deepseek-ai/dsh@<version>` within hours of a GitHub pre-release; update automation that pins exact versions
- **Action level**: informational
- **Symptoms**: `dsh-v0.1.6-alpha.2` was published on GitHub releases (tag `ddefc45`) but `npm view @deepseek-ai/dsh@0.1.6-alpha.2` returned E404 for at least the first minutes-to-hours; `dist-tags.alpha` still pointed at 0.1.6-alpha.1. An upgrade attempt in that window fails with "No match found for version".
- **Migration recipe**: Poll `npm view` until the version resolves before killing the running host — never start the stop-host phase against an unpublished version. Fallbacks (build from the git tag) are discouraged: the repository root is a private pnpm monorepo (`@deepseek-ai/dsh-root`), so a git/tree install does not produce the published `@deepseek-ai/dsh` package and hand-built trees violate the formal-install rule.
- **Verification**: `npm view @deepseek-ai/dsh@<version> version` resolves before starting the upgrade; after install, `dsh --version` prints exactly the pinned version.
- **Source**: [dsh-v0.1.6-alpha.2 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.6-alpha.2) · first-hand (2026-09-17: E404 observed through three polls ~7 minutes after the GitHub release; npm alpha tag still `0.1.6-alpha.1`)
