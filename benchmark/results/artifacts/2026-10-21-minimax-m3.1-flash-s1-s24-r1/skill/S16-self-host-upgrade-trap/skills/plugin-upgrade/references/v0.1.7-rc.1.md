### DSH-0.1.7-RC1-01 · DSH peer ranges are enforced at install and at startup; `^0.1.7` does not admit `0.1.7-rc.1`

- **Type**: breaking
- **Applies to**: every plugin package and plugin bundle that declares a `peerDependencies` key named `@deepseek-ai/dsh` or `@deepseek-ai/dsh-*`; fleet install scripts that drive `dsh plugin add` / `install`
- **Touchpoints**: none (packaging/dependencies special surface — pre-flight §0 `peerDependencies` inventory); #7 when a script parses `dsh plugin` exit status or stderr
- **Action level**: required-if-hit
- **Symptoms**:
  - **What is checked.** Up to alpha.2 a DSH peer range was advisory. From rc.1, app-boot compares each DSH peer range against the one runtime version (the app-boot `package.json` version, `0.1.7-rc.1`). The check is `semver.satisfies(runtime, range, { includePrerelease: true })`, using the `semver ^7.8.5` app-boot depends on.
  - **Install time.** `dsh plugin --profile <p> add <spec>` refuses a mismatching plugin before pnpm runs and exits 1. stderr shows `dsh: installation rejected: Plugin <name>@<version> is incompatible with dsh 0.1.7-rc.1: peerDependencies {...}. Running it may cause crashes or data loss. …`, then `dsh: nothing was installed.`, then a ready-made `allow-version` command.
  - **Startup.** An already-installed mismatching plugin row is disabled in the launcher's in-memory copy: stderr shows `dsh: disabling profile plugin row "<id>": Plugin … is incompatible …`. The profile files are not modified, so the row silently stops mounting.
  - **The semver 7.8.3 trap.** Starting with semver 7.8.3, `^0.1.7` under `includePrerelease` expands to `>=0.1.7 <0.2.0-0`; 7.8.0–7.8.2 and 7.7.x still expanded it to `>=0.1.7-0 …` and admitted `0.1.7-rc.1`. So on a host that resolves semver ≥ 7.8.3 (app-boot declares `^7.8.5`), a plugin whose floor is already written as `^0.1.7` is refused by every 0.1.7 prerelease. Only the caret form depends on the semver version: `~0.1.7` and `>=0.1.7` are refused by every semver version, with or without `includePrerelease`. Measured against `0.1.7-rc.1` with semver 7.8.5 and `{ includePrerelease: true }`:

    | Result | Ranges |
    |---|---|
    | Refused | `^0.1.7`, `~0.1.7`, `>=0.1.7`, `0.1.7`, `0.1.7-alpha.2` (exact prerelease pins), `^0.1.8`, `""` |
    | Admitted | `^0.1.7-0`, `~0.1.7-0`, `^0.1.7-rc.1`, `^0.1.7-alpha.2`, `^0.1.6`, `~0.1.6`, `^0.1.5`, `^0.1.5-rc.2`, `0.1.x`, `>=0.1.5`, `>=0.1.5 <0.1.7`, `<0.2.0`, `*` |
- **Migration recipe**:
  1. **Inventory.** List every `@deepseek-ai/dsh*` key in the plugin's `peerDependencies`. Other `@deepseek-ai/*` keys (for example `@deepseek-ai/cordis`), `dependencies` and `engines` are not checked, and a plugin with no DSH peer is never refused.
  2. **If the target host is a 0.1.7 prerelease**, rewrite each refused floor so it admits prereleases:
     - `^0.1.7` / `~0.1.7` / `>=0.1.7` → `^0.1.7-0` (or `^0.1.7-rc.1` to exclude older alphas);
     - exact pins → a caret range.

     This relaxes the "no `-rc` suffix survives" rule in [precision-checklist.md](precision-checklist.md#peer-version-floors--exact-values-not-newer-carets): that rule was written for a final-release target cohort. When the target is itself a prerelease, the floor must carry a prerelease tag or sit below the target minor.
  3. **Keep `workspace:^` / `workspace:~` / `workspace:*`** in source launches. They are treated as the running version and always pass.
  4. **Keep every peer value a string.** A non-string value makes the manifest unverifiable, and the plugin is refused.
  5. **Only if you deliberately run a mismatching build**, grant an exemption for the exact plugin version and the exact DSH version:

     ```sh
     dsh plugin --profile <p> allow-version <name>@<version> --dsh-version 0.1.7-rc.1 --accept-risk
     ```

     Then retry the install or restart. Grants are stored in `<profile>/compatibility.json` as `{ "<name>@<version>": ["<dsh version>"] }`. They are not carried over when either the plugin or DSH changes version.
     - Review grants with `dsh plugin --profile <p> version-exemptions`; revoke with `revoke-version <name>@<version> --dsh-version <v>`.
     - In the plugin manager, the matching `plugin_manager` tool actions are `list_version_exemptions` / `set_version_exemption` (`acceptRisk: true`), and the Remote methods are `listVersionExemptions()` / `setVersionExemption(...)`.
     - An exemption does not authorize dependency scripts.
- **Verification**: `--dump-config` is not enough to prove a plugin still mounts.
  - **The trap.** After a denial the row still appears in `dsh --profile <p> --dump-config` exactly as before, and nothing is written to stderr. Only an incompatible plugin **bundle** drops out of the dump (it is skipped like an unreadable bundle).
  - **Instead:**
    - boot the target host once and assert its stderr has no `disabling profile plugin row` line for your ids;
    - for install paths, assert `dsh plugin add` exits 0 with no `installation rejected`.
  - This also applies to the `plugin-release` skill's step 1.4, whose `--dump-config` row check cannot detect a denial on rc.1 and later.

  - With the `^0.1.7` row inserted through `cordis.patch.yml` and the grant revoked, `--dump-config` still printed the row with an empty stderr, while a real boot printed `dsh: disabling profile plugin row "probe-caret": …`.
  - The same semver matrix under 7.7.4 and 7.8.0–7.8.2 admits `^0.1.7` (`~0.1.7` and `>=0.1.7` stay refused in every version). Any compatibility pre-check a fleet runs with its own semver copy must use semver ≥ 7.8.3 (ideally the host's own `^7.8.5`) **and** call it the way the host does, `semver.satisfies(runtime, range, { includePrerelease: true })`. ### DSH-0.1.7-RC1-02 · `tool.call.toolview` owners become a phase union; `RunningToolCall` splits into preparing and started calls

- **Type**: breaking
- **Applies to**: Web Client plugins that register a keyed `tool.call.toolview` entry, or that read `RunningToolCall` / `ToolCallBlock` from `ui-conversation` / `ui-chat`
- **Touchpoints**: #5 (UI slots / tool views)
- **Action level**: required-if-hit
- **Symptoms**:
  - **New preparing stage.** Tool calls now render in three stages: `preparing` (the model has named the tool but its arguments are still streaming), `start` and `result`. Registered keyed views are rendered during `preparing` too.
  - **Record type split** (`ui-conversation` `contract/records.ts`). `RunningToolCall` used to be one interface that always carried `argsRaw`. It is now `PreparingToolCall | StartedToolCall`, discriminated by `phase: 'preparing' | 'start'`, and `argsRaw` exists only on `StartedToolCall`.
    - Both variants share `callId`, `parentCallId?`, `name`, `turn`, `step`, `subCalls`, and `time` (now "when this stage began").
  - **Owner props** (`ui-tool` `contract/slots.ts`). `ToolCallOwnerProps` used to be one interface with `block: ToolCallBlock`. It is now `ToolCallCommonProps & ToolCallPhaseProps`, where the phase part is `{ phase: 'preparing', block: PreparingToolCall } | { phase: 'start', block: StartedToolCall } | { phase: 'result', block: ToolResultNode }`.
  - **What breaks.**
    - A view that reads `block.argsRaw` without narrowing no longer typechecks.
    - At runtime during live streaming, the same view receives a preparing block whose `argsRaw` is `undefined`. `JSON.parse(undefined)` throws, and so does `argsRaw.length`.
    - Preparing calls render no sub-calls.
    - Reloaded history goes straight from start to result, so a view that only looks correct on reload can still crash live.
- **Migration recipe**:
  1. Narrow on `props.phase` before touching `block.argsRaw` or dispatched-call material.
  2. Render a light placeholder (tool name, spinner) for `'preparing'`.
  3. To show arguments as they stream, add `inject: { hooks: { toolCallArgumentsPartial } }` to the toolview entry. Then call the injected hook `useToolCallArgumentsPartial()`: it returns the raw argument prefix (a partial JSON string, so do not `JSON.parse` it blindly) and an empty string outside `preparing`.
  4. Existing argument/result components that never want the preparing stage can be typed with the new `StartedToolCallViewProps`, which excludes it; gate their use on `props.phase !== 'preparing'`.

  New exports: `ToolCallCommonProps`, `ToolCallPhaseProps`, `StartedToolCallViewProps`, `ToolCallHookContext`, `ToolCallInjected`, `UseToolCallArgumentsPartial` from `ui-tool`; `PreparingToolCall`, `StartedToolCall` from `ui-conversation` (re-exported by `ui-chat`).
- **Verification**: typecheck against the rc.1 `ui-tool` / `ui-conversation` types. Then trigger your tool live with arguments large enough to stream for a visible moment, and assert that the view shows the preparing placeholder with no page error, and that the start and result views match the pre-upgrade rendering.
- **Source**: [d3086e6571](https://github.com/deepseek-ai/deepseek-harness/commit/d3086e6571) `feat(chat): present tools in preparing, start, and result stages`; [`.agents/notes/implemented/architecture/2026-09-22-tool-call-three-phases.md`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.7-rc.1/.agents/notes/implemented/architecture/2026-09-22-tool-call-three-phases.md); [`packages/client/ui-conversation/src/client/contract/records.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.7-rc.1/packages/client/ui-conversation/src/client/contract/records.ts), [`packages/client/ui-tool/src/client/contract/slots.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.7-rc.1/packages/client/ui-tool/src/client/contract/slots.ts), [`packages/client/ui-tool/src/client/tool/tool-call-arguments-partial.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.7-rc.1/packages/client/ui-tool/src/client/tool/tool-call-arguments-partial.ts) at `dsh-v0.1.7-rc.1`.

### DSH-0.1.7-RC1-03 · Conversation Definitions: transient events may start a Context; a repeated start becomes an update

- **Type**: behavior
- **Applies to**: plugins that implement a custom `ConversationNodeDefinition` (`UiConversation.events`)
- **Touchpoints**: #5 (UI conversation nodes); #2 when the Definition matches plugin-owned session events
- **Action level**: conditional
- **Symptoms**:
  - **Transient starts accepted.** `ConversationStartMatch` changes from `ConversationMatchOf<SessionEvent, 'start'>` to `ConversationMatchOf<SessionEventLike, 'start'>`: a Client-only transient event (for example a live chunk) may now start a Context. alpha.2 rejected transient starts.
  - **Later starts become updates.** The earliest currently loaded start initializes State. Every later Match, including another `role: 'start'` for the same id, goes to `update()`. The assembler no longer throws on a second start, so accidental id reuse across logically distinct nodes is no longer detected — the two merge silently into one Context.
  - **Settlement.** Settlement recomputes a Context from its remaining earliest start. A Context whose only start was transient and has been removed has no State.
- **Migration recipe**:
  1. Make `update()` accept a Match whose role is `start`: treat it as a restatement, not an error.
  2. If `start()` assumed a durable `SessionEvent` (for example reading `seq` ordering or durable-only fields), handle the transient `SessionEventLike` shape, or return `null` from `match()` for transient events you never want as a start.
  3. Make Definition ids unique per logical node, since collisions are no longer reported.
- **Verification**: stream a turn that produces your node live; assert a single node is rendered. Reload the session and assert the same node and state rebuild from durable events alone.
- **Source**: [d550f1c4af](https://github.com/deepseek-ai/deepseek-harness/commit/d550f1c4af) `feat(conversation): initialize contexts from transient start matches`; [`packages/client/ui-conversation/src/client/contract/conversation.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.7-rc.1/packages/client/ui-conversation/src/client/contract/conversation.ts) and [`packages/client/ui-conversation/README.md`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.7-rc.1/packages/client/ui-conversation/README.md) at `dsh-v0.1.7-rc.1`.

### DSH-0.1.7-RC1-04 · Work-detail setting gains four modes; the default moves from `compact` to `standard`

- **Type**: behavior
- **Applies to**: Web Client plugins that read or write the chat `transcriptView` setting, or branch on `TranscriptViewMode`; fleet screenshots/snapshot baselines of the chat transcript
- **Touchpoints**: #5 (UI settings consumers)
- **Action level**: conditional
- **Symptoms**:
  - **Mode list.** In `@deepseek-ai/dsh-ui-chat` `chat-settings.ts`, `TRANSCRIPT_VIEW_MODES` goes from `['compact', 'detailed', 'expanded']` to `['compact', 'standard', 'detailed', 'verbose']`.
  - **Default.** `DEFAULT_TRANSCRIPT_VIEW_MODE` goes from `compact` to `standard`.
  - **Legacy values.**
    - A saved `expanded` is read as `detailed` and never written back (`LEGACY_EXPANDED_TRANSCRIPT_VIEW_MODE`).
    - The two-mode legacy value `normal` is read as `standard` (`LEGACY_TRANSCRIPT_VIEW_MODE`).
    - Missing or unrecognized values fall back to `standard`.
  - **What breaks.**
    - Code with a `switch` over the old three modes has no `standard` or `verbose` branch.
    - Code that writes `expanded` no longer gets an offered mode.
    - Screenshots of users with no explicit preference change, because the default is no longer `compact`.
- **Migration recipe**:
  - Handle all four modes.
  - Write only values from `TRANSCRIPT_VIEW_MODES`.
  - Import the constants instead of hard-coding strings.
  - Re-baseline transcript snapshots taken under the old implicit `compact` default, or pin `transcriptView` explicitly in the test profile.
- **Verification**: open settings and cycle all four modes with your plugin's UI mounted; assert no fallback branch is hit. Start a profile with no saved preference and assert it renders as `standard`.
- **Source**: [015a9b202c](https://github.com/deepseek-ai/deepseek-harness/commit/015a9b202c) `feat(chat): add four work detail modes and legacy mappings`; [`packages/client/ui-chat/src/chat-settings.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.7-rc.1/packages/client/ui-chat/src/chat-settings.ts) at `dsh-v0.1.7-rc.1`.

### DSH-0.1.7-RC1-05 · Plugin Manager bounds silent pnpm runs and prechecks GitHub reachability before installing

- **Type**: behavior
- **Applies to**: service-driven plugin installs (plugin manager tool / Remote); plugins installed from GitHub specs; automation that interprets install failures
- **Touchpoints**: #7 (subprocess output and failure classification)
- **Action level**: informational
- **Symptoms**:
  - **Silent-run timeout.** A service-driven pnpm run whose captured output stays silent for `idleTimeoutMs` (default `600000`) is terminated along with its whole process tree. It reports `timedOut`, is classified `timeout` whatever exit status the signal left behind, is not retried on the next registry, and restores the profile files.
    - A run now completes when its process exits; the pipes then get a bounded drain, so a lifecycle-script descendant can no longer hold the operation (and the profile lock) open.
    - `dsh plugin` on the CLI inherits the terminal and remains unbounded.
  - **GitHub precheck.** Installs from GitHub repository specs first run `git ls-remote`, bounded by `githubConnectionTimeoutMs` (default `5000`), with credential helpers and prompts disabled.
    - Only network failures and timeouts stop the install; they report `failedAt: 'spec-host'` and offer mirror recovery.
    - Authentication and lookup failures are still left to pnpm, including its HTTPS-to-SSH fallback.
    - Registry, path, tarball and non-GitHub Git specs skip the check.
- **Migration recipe**: no plugin action.
  - Plugins whose install runs a long, silent postinstall (native builds, large downloads without progress output) should print progress or document raising `idleTimeoutMs`.
  - Automation that retried on generic failures should treat `timeout` and `failedAt: 'spec-host'` as distinct, non-transient-by-registry outcomes.
- **Verification**: for a plugin with a heavy postinstall, run the service-driven install once and assert it completes without a `timeout` classification. For a GitHub spec behind a blocked network, assert the failure names `spec-host` within about 5 s rather than hanging.
- **Source**: [ccaa0dc11c](https://github.com/deepseek-ai/deepseek-harness/commit/ccaa0dc11c) `fix(plugin-manager): bound pnpm runs so a silent child cannot hold the profile lock (#4982)`, [0edfe83573](https://github.com/deepseek-ai/deepseek-harness/commit/0edfe83573) `fix(plugin-manager): bound GitHub connection checks before installation`, [d6e5b7e41a](https://github.com/deepseek-ai/deepseek-harness/commit/d6e5b7e41a), [75d74a055e](https://github.com/deepseek-ai/deepseek-harness/commit/75d74a055e); [`packages/boot/plugin-manager/README.md`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.7-rc.1/packages/boot/plugin-manager/README.md) (configuration table and operations section) at `dsh-v0.1.7-rc.1`.
