2) WHY NPM WAS SILENT
- npm's peer check compares version strings: is the installed cohort (0.1.2-alpha.5) inside the declared range (^0.1.2-alpha.2 => >=0.1.2-alpha.2 <0.2.0-0)? Yes, so there is no warning to emit (fixture/npm-install-output.txt).
- What ^0.1.2-alpha.2 guarantees: the peer package identity resolves in the graph inside the range; the resolver keeps the cohort coherent; the author's claim is at least arithmetically well-formed. npm never loads the plugin or inspects any API surface, so it cannot verify the claim is TRUE.
- What it does NOT guarantee: that any specific export/getter/method/field/event the plugin uses still exists (Session.events is the proof - the package identity is right, the member is gone); that the plugin works at every version inside the range; anything whatsoever at runtime; that 'newer is compatible' (alpha.5 > alpha.2 is a label-ordering fact, not API containment); that the corridor is free of breaking changes - for 0.x semver reserves the MINOR position for breaking changes, so the 0.1.2-alpha.* stream is one 'minor' line and alpha.4 alone shipped 4 breaking cards (A4-01 package removed, A4-02 package renamed, A4-03 Session.events removed, A4-04 types re-branded). Also: engines is environment (Node), not host API, and npm's EBADENGINE is a warning; and under npm's prerelease tuple rule a prerelease floor on 0.1.2 also refuses later cohorts such as 0.1.3-alpha.1 (derived from rollup R-08, not measured here).

3) THE PRINCIPLE + BREAKAGE CATEGORIES
- Peer-range satisfaction = a STATIC, package-metadata-level check (does version V satisfy range R?). It is a NECESSARY but not sufficient condition for compatibility; it is cheap by design, which is why it cannot carry the semantic weight people load onto it.
- Runtime compatibility = a BEHAVIOURAL, code-level check (does every member this code touches still exist, with the same shape/semantics/timing, in the version that will actually run?).
- Formal difference: peer satisfaction is a claim about ORDERING; runtime compatibility is a claim about SET MEMBERSHIP ('is member events in the API of version V?'). Semver provides an order, never containment between two releases' API sets.
- Categories that pass peer validation and crash at runtime: (a) removed/renamed API member inside the range - THIS INCIDENT (Session.events; sibling shapes: package removed A4-01, package renamed A4-02); (b) changed signature/shape of a surviving member (ctx.commands.execute gained an 'images' arg - rollup R-11; seedLength -> isSeeded+inheritedEventCount A4-04; branded SessionSeq/SessionLogOffset); (c) behavioural/default change with no removal (web_fetch on by default A4-06; workflow tool gone from PTC preset A4-05); (d) event/wire contract drift (A1-01/02/06; history atSeq tightening); (e) composition-plane breakage - installs and version-matches but never activates (require:['apiProxy'] pending forever A1-01; inject naming a removed package A1-25; row-name mismatch A1-26); (f) type-vs-runtime divergence - R-11 'static drift'; a JS plugin (this one, channel.js) gets NO compile-time signal at all, which is why (a) shipped.
- Note: from dsh 0.1.7-rc.1 onward the host itself ENFORCES DSH peer ranges at install and startup (card DSH-0.1.7-RC1-01 / DSH-0.1.7-J1-01: refused install with incompatible-version, plugin disabled at boot, exact-version exemptions in <profile>/compatibility.json). That is a stronger version of the SAME static check and still could not have caught this plugin, because the plugin's range was simply WRONG. Enforcement cannot repair an incorrect claim.
