# Change cards · 0.2.0-rc.2

First-hand evidence for this edge comes from a real Desktop 0.2.0-rc.2 install
(Windows) exercised during a third-party plugin migration
([@alexpeng/dsh-custom-plugin](https://github.com/AlexPeng07/dsh-custom-plugin)
0.6.0 → 0.7.0, September 2026), cross-checked against the `dsh-v0.2.0-rc.2`
tag source. The two Desktop observations previously kept as uncarded field
notes at the end of [v0.2.0-rc.1.md](v0.2.0-rc.1.md) are folded in here as
DSH-0.2.0-RC2-A1-02 and DSH-0.2.0-RC2-A1-03 with their original sources.

Whether the Desktop runner behavior described below already existed at
0.2.0-rc.1 was not tested; the cards state the verified 0.2.0-rc.2 behavior
and what a plugin must do about it.

---

### DSH-0.2.0-RC2-A1-01 · Desktop shell forwards renderer requests through `dsh-app://app` after deleting `host`/`origin`/`cookie`/`sec-fetch-site` — plugin fences that require an affirmative browser marker 403 every route on Desktop

- **Type**: breaking
- **Applies to**: every plugin whose host half puts `/api/...` routes (and any
  plugin-served script route) behind a trust fence that requires an affirmative
  browser marker — `sec-fetch-site: same-origin` or an `origin` header — i.e. a
  fence that copies the platform fence's header *shape* instead of its trust
  semantics. State-changing routes fail worst: the UI keeps showing the old
  state while saves never persist, so the breakage reads as "settings don't
  stick" rather than "forbidden".
- **Touchpoints**: #6 (custom HTTP / WS channels)
- **Action level**: required-if-hit
- **Symptoms**:
  - On Desktop, every plugin HTTP route and plugin-served script returns 403
    while the identical plugin build on the Web host (default port 3080) works.
    Everything the plugin serves through its own routes fails at once:
    exports, search, engine fetch, balance, and all state saves.
  - The Desktop renderer runs at `dsh-app://app`, not an http(s) origin, so no
    request it issues can carry a meaningful same-origin `origin` header.
  - `--dump-config` cannot see this: the plugin activates and its rows mount;
    only the request fence rejects.
- **Migration recipe**: implement the fence with the platform fence's *trust
  semantics*, not an affirmative browser marker:
  1. require a loopback socket with a loopback `Host` header;
  2. reject `sec-fetch-site: cross-site`;
  3. accept `origin` when it is **absent or equals the Host authority** —
     absent markers are trusted, because the Desktop shell deletes
     `host`/`origin`/`cookie`/`sec-fetch-site` before forwarding (source below),
     and the shell itself already refused any attached origin other than
     `dsh-app://app`;
  4. do not require cookies or CSRF tokens on loopback plugin routes: the
     forwarded request carries the Host's own auth cookie, not the renderer's.
  WebSocket upgrades are covered too: the shell rewrites `origin` to the Host
  authority and sets `sec-fetch-site: same-origin` for `ws://127.0.0.1/*`
  requests originating from `dsh-app://app`, so the same fence passes WS.
- **Verification**: probe the Desktop Host (default `127.0.0.1:19387`) with
  exactly the shell's forward shape — loopback socket, loopback `Host`, no
  `origin`, no `sec-fetch-site`, no `cookie` — and expect 200; repeat with a
  foreign `origin` and with `sec-fetch-site: cross-site` and expect 403. One
  request per plugin route is enough. First-hand: an 11-probe suite (desktop
  forward shape, desktop WS shape, foreign origin, cross-site, malformed
  origin, non-loopback Host, and per-route liveness) passed 11/11 on a real
  Desktop 0.2.0-rc.2 install (Windows).
- **Source**: [`apps/desktop/src/web-document.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.0-rc.2/apps/desktop/src/web-document.ts)
  (`forwardWebRequest`: rejects any attached origin other than `dsh-app://app`,
  then `headers.delete` for `['host', 'origin', 'cookie', 'sec-fetch-site']`,
  sets the Host auth cookie) and
  [`apps/desktop/src/main.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.0-rc.2/apps/desktop/src/main.ts)
  (`protocol.handle` forwards non-asset `dsh-app://app` paths to the Host;
  `onBeforeSendHeaders` for `ws://127.0.0.1/*` rewrites `origin` and sets
  `sec-fetch-site: same-origin`), both at tag `dsh-v0.2.0-rc.2`.
- **Field note** (first-hand, 2026-09-30): `@alexpeng/dsh-custom-plugin@0.6.0`
  on Desktop 0.2.0-rc.2 (Windows): every `/api/custom-plugin/*` route and the
  plugin's mermaid script route returned 403 `forbidden` — exports, session
  search, mermaid fetch and in-place rendering, balance, and **all state saves**
  (appearance, folders, prompts persisted on Web, never on Desktop). Root cause
  was the fence requiring `sec-fetch-site: same-origin` or an `origin` header.
  Fixed by realigning the fence trust semantics as in the recipe above;
  shipped as 0.7.0 with fence-level unit tests and the 11-probe desktop shape
  suite ([AlexPeng07/dsh-custom-plugin](https://github.com/AlexPeng07/dsh-custom-plugin),
  commit `9d40fbe`).

### DSH-0.2.0-RC2-A1-02 · Desktop host: the plugin-visible `ctx.sessions` registry is empty — plugins resolving the session cwd through `sessions` fail on Desktop while working on Web

- **Type**: breaking
- **Applies to**: every plugin whose host half resolves the running session (or
  its workspace cwd) via `ctx.sessions.get(sessionId)`; install flows that rely
  on such plugins on the Desktop profile
- **Touchpoints**: #3 (internal service probes / Remote); special surface: the
  Desktop runner (`dsh-desktop-host` → `runProfile`) instead of the CLI app-boot
- **Action level**: required-if-hit
- **Symptoms**:
  - On the Desktop host, `ctx.sessions.get(id)` returns `undefined` for **every**
    id, including a session the same host is actively running (its
    `session.v4.jsonl.zstd` is being appended at that moment). The plugin's
    cordis `inject: ['webServer', 'loader', 'sessions']` still resolves and the
    plugin activates — a service named `sessions` exists, but its live-session
    registry reads empty from a plugin fiber.
  - The Web host with the identical dsh version, profile bundles, and plugin
    tree works: the same probe flow (batch → file PUT → commit) completes and
    files land under `<workspace>/.dsh/tmp/attachments/`.
  - User-visible: a paste/attachment plugin's chips render but resolve
    "unavailable" (no file is ever written) and sending fails.
  - Unverified suspicion: the Desktop runner boots the composition with a
    different cordis fiber/isolate layout than the CLI app-boot, so the
    `sessions` service a plugin resolves is not the registry the agent runtime
    populates.
- **Migration recipe**: plugin-side workaround, verified first-hand — no host
  changes needed.
  1. **Session resolution fallback**: when `ctx.sessions.get(sessionId)`
     misses, resolve the workspace through `ctx.get('workspaceRegistry')` —
     the registry maps header-validated `sessionIds` to canonical workspace
     `path`s (`resolve(workspace.path)` is the cwd). Still entirely
     server-side: no client-supplied path enters the resolution, so the
     original security model holds. Keep the canonical lookup first; the
     fallback changes nothing on Web. Shipped and verified in
     `dsh-paste-input` v0.2.6.
  2. **Binary request bodies do not survive `dsh-app://` forwarding either**:
     a Blob PUT arrives with a declared `Content-Length` that no longer
     matches the received bytes (the body is re-encoded in a text-safe way),
     so any size/content validation rejects it. Ship a base64-JSON transport
     for the Desktop origin (`location.protocol === 'dsh-app:'` detection;
     e.g. `POST .../files/<n>/base64` with `{ "data": "<base64>" }`, server
     decodes and checks the decoded length against the declared size) and
     keep the binary fast path on Web. Verified end-to-end: paste → upload →
     commit → file lands under `<workspace>/.dsh/tmp/attachments/`.
  3. Track the upstream reports:
     [discussion #8303](https://github.com/deepseek-ai/deepseek-harness/discussions/8303)
     (includes the confirmed workaround) and the companion issue in the
     dsh-external beta channel.
  4. Re-verify after every Desktop release: one `POST` against the plugin's
     session-resolving endpoint with a live session id is enough to see `200`
     vs the `live session not found` family of failures; once the host
     registry is fixed the fallback simply stops firing.
- **Verification**: on the Desktop host, with one session running, call a
  plugin endpoint that starts from `ctx.sessions.get(sessionId)`; assert the
  resolved session and `session.header.cwd`. `--dump-config` cannot see this:
  the plugin mounts and serves; only the session lookup fails.
- **Source**: [`packages/api/session-controller`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.0-rc.2/packages/api/session-controller)
  and the Desktop runner entry at `apps/desktop-host` at tag `dsh-v0.2.0-rc.2`.
- **Field note** (first-hand, 2026-09-29): unauthenticated probes against the
  Desktop host (127.0.0.1:19387): `GET /dsh-paste-input/v1/latest → 200` (host
  half mounted), `POST /dsh-paste-input/v1/batches → 400 "live session not
  found: <id>"` for both a live and a persisted session id. Same probes on the
  Web host (port 3080, same rc.2) complete the whole upload flow. Reported
  upstream as [discussion #8303](https://github.com/deepseek-ai/deepseek-harness/discussions/8303).
  (Observed on Desktop 0.2.0-rc.2; previously kept as an uncarded field note at
  the end of [v0.2.0-rc.1.md](v0.2.0-rc.1.md).)

### DSH-0.2.0-RC2-A1-03 · Desktop host spawns tool subprocesses with a minimal `PATH`; `pwsh` is not resolvable on Windows

- **Type**: behavior
- **Applies to**: plugins and skills whose host-side code shells out to
  platform tools resolved from `PATH` (package managers, shells, git);
  anything assuming the CLI login-shell environment on Desktop
- **Touchpoints**: #7 (subprocess / stdout / stderr parsing)
- **Action level**: conditional
- **Symptoms**: subprocesses spawned by sessions on the Desktop host see a
  minimal `PATH` — `System32` tools resolve, but `pwsh` does not
  (`spawnSync pwsh ENOENT`). The 0.2.0-rc.2 release notes fix the missing
  login-shell environment for macOS/Linux graphical launches; Windows Desktop
  appears to still need the equivalent.
- **Migration recipe**: resolve executables by absolute path when the
  environment is known (derive from well-known install locations), or degrade
  with a clear message instead of relying on `PATH` lookup on the Desktop
  profile.
- **Verification**: from a Desktop-hosted session, spawn
  `pwsh -Command '$PSVersionTable.PSVersion'` and observe ENOENT; the same
  spawn from a Web-hosted session succeeds.
- **Source**: [`apps/desktop/README.md`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.0-rc.2/apps/desktop/README.md)
  and the macOS/Linux login-shell fix in the
  [rc.1 → rc.2 compare](https://github.com/deepseek-ai/deepseek-harness/compare/dsh-v0.2.0-rc.1...dsh-v0.2.0-rc.2)
  (`fix(desktop): supply login shell environment on macOS and Linux graphical launches`).
- **Field note** (first-hand, 2026-09-29): a tool subprocess under the Desktop
  host failed `spawnSync pwsh` with ENOENT while `netstat`/`wmic` (System32)
  resolved normally; the identical spawn from the Web host worked. (Observed on
  Desktop 0.2.0-rc.2; previously kept as an uncarded field note at the end of
  [v0.2.0-rc.1.md](v0.2.0-rc.1.md).)

### `sessionQuery.readSession()` replay-validates seeded (forked/resumed) sessions and rejects any whose log outgrew its seed boundary — exports/timeline/search fail with "seeded session constructor seed must equal its inherited prefix"

- *Type*: breaking
- *Applies to*: plugins that read session logs through
  `sessionQuery.readSession()` for any seeded (forked or resumed) session
- *Symptoms*: `readSession` throws `seeded session constructor seed must equal its inherited prefix or mark its inherited cut` — in the shipped rc.2 package the snapshot-mode constructor rejects when `header.isSeeded && inheritedEventCount !== log.length` unless a `session/end-seed` marker with `inherited: true` marks the cut; timeline, export,
  in-session search, and usage replay all fail with the wrapped message.
- *Migration recipe*: fall back to `observeSession` (live/restore paths,
  `projectionMode: 'none'`) when `readSession` rejects, and keep the fallback
  permanently — it simply stops firing if the host-side validation changes.
  The guard must stay explicit: a host without `observeSession` should surface
  the original error, not a TypeError about a missing method.
- *Verification*: on a dsh build with the validation, export a forked session
  and observe the wrapped error; with the fallback, the same export succeeds.
- *Source*: the shipped `@deepseek-ai/dsh-session` at `dsh-v0.2.0-rc.2`
  contains the validation (first-hand package inspection, 2026-10-03; the 2026-09-12 observation reported the shorter message form — the message and the marker escape have since evolved). First
  observed 2026-09-12 on the then-current dsh build during the
  [@alexpeng/dsh-custom-plugin](https://github.com/AlexPeng07/dsh-custom-plugin)
  0.4.2 release (commit `30e025b`); the exact dsh tag that introduced it is
  **not verified** — check the target tag before treating this as an edge card.
