## 2. 语义走廊：这个标记的完整历史

`ignorable` 不是装饰性字段，它是**持久事件的"可跳过"许可**：生产者声明"这条事件是信息性的，不认识它的 reader 可以跳过而不是让整段日志解析失败"。它的存在与否直接决定**跨版本可读性**（新旧 reader 互读对方写的日志）。走廊按版本展开：

**阶段 0（alpha.1 之前，基线）**
字段在事件契约中，语义有效：reader 把它当许可，生产者按需声明。此时第三条不变式成立——**标记由生产者声明，由 reader 尊重**。

**阶段 1（alpha.1，DSH-0.1.2-A1-02）：字段被"临时移除"**
关键点在于移除了什么、又没有移除什么：

- 被移除的是**字段本身**（契约窗口收缩），而不是"字段必须被删除"这条新规则；
- 字段不存在时，reader 侧**不可能**因为一个不存在的字段而拒绝事件——没有可拒绝的对象；
- 生产者侧此时**无处声明**，正确反应是"少写一个字段"，不是"主动执行一次删除动作"。

防御代码把"字段被移除"误读成了"字段被禁止存在，故必须先抹掉"。这是一个范畴错误：**缺席不需要被制造。**

**阶段 2（alpha.2，DSH-0.1.2-A2-01）：恢复保留语义（remove-then-restore）**
字段回到契约，reader 重新把"可跳过"当许可。走廊终点 = 字段在场且有效。

**走廊推论（决定性的那一步）**
任何一个以"阶段 1 的空缺"为前提的 workaround，其生命周期严格被夹在阶段 1 与阶段 2 之间。阶段 2 一到，前提消失，workaround 必须退出——它不是"可以保留的历史包袱"，而是**方向上已经反了的代码**。注释把阶段 1 的临时状态写成了跨版本的永久约束（"迁移到 alpha.2 时这段要继续保留"），而 A2-01 与该断言直接冲突：**在走廊里，注释是滞后的一方。**

## 3. 代码级证据（不依赖注释的四条硬事实）

**E1 · delete 是 no-op（已实测）**
事件由字面量 `{ type, payload }` 构造，从不含 `ignorable`。实测（Node，同一语言语义）：

```
delete e.ignorable            → true
Object.keys(e)                → ["type","payload"]   // 未变
'ignorable' in e              → false                 // 本来就没有
```

即：这段"防御"在 alpha.1 里**没有保护过任何东西**，在 alpha.2 里**默认也不破坏任何东西**。它是一段自我描述的代码：唯一产出是让读者以为存在一个已经被处理过的风险。

**E2 · 注释的因果链在其自身代码里断裂**
"不删 marker 会被 reader 拒绝"要成立，需要事件上**先有** marker。代码路径上不存在该前提，因此该断言在本文件内既不可触发、也无从验证。按"以证据定案"的原则，应判为**无来源断言**，不能作为保留理由。这正是本题的陷阱形态：一段没有对应风险的防御，靠注释自我授权。

**E3 · `as any` 把契约问题降级为一次静默逃逸**
`delete (event as any).ignorable` 同时做了两件事：绕开类型检查，并把"字段该不该在场"这个**契约级**决定搬到运行时手工抹除。alpha.2 的正确姿势是让类型系统回答这个问题；用 `as any` 抢答，等于把编译器变成了旁观者。

**E4 · 潜伏的破坏性（唯一可能的"效果"是有害的那个）**
一旦事件构造方式演进——例如 `{ ...base, ...payload }`，或上游把 `ignorable: true` 放进 base——这行 delete 会**静默剥掉保留标记**，事件从"可跳过"变成"必须理解"：老 reader 遇到不认识的事件类型时必须失败。**这正是 A2-01 恢复该语义要防的场景。** 换言之，这段代码的全部潜在影响力，方向与 alpha.2 的意图相反；而属性删除带来的隐藏类惩罚，也只在属性真的存在（即 E4 场景）时才发生。

**E5 · 注释与代码互相漂移**
注释同时承担了历史陈述（A1-02）与未来指令（"要继续保留"）。前者与走廊一致，后者与 A2-01 冲突。**一段同时包含正确历史与错误指令的注释，不能作为行为证据**——这解释了为什么本题要求"由证据判定"。

## 4. 处置决定：删除

**删除这行 delete，以及那条误导性注释；不要用"等价物"替换。**

三条边界，避免把"删防御"做成"换个姿势继续防御"：

1. **不要**把 `delete` 改成 `ignorable: false`。那是把"抹除"换成"显式否认"，同样是在替 reader 做决定，而且会把一条信息性事件错误地标成载荷性。
2. **不要**为了保住注释而保留死代码。删除后行为零变化（E1），所以这是纯清理，回归风险仅来自"有人真的依赖了它"——而 E1 证明无人可以依赖。
3. **如果**该插件确实要声明可忽略性（`third-party/informational` 从命名看属信息性事件，但见 §6），正确写法是在构造事件时**声明**，方向与删除相反：

```ts
export function produceExternalEvent(session: Session, payload: Payload): void {
  // alpha.2: 保留语义已恢复（DSH-0.1.2-A2-01）。第三方信息性事件声明为可忽略，
  // 使不认识该类型的 reader 可以跳过，而不是让日志解析失败。
  session.append({ type: 'third-party/informational', payload, ignorable: true })
}
```

（若 alpha.2 的公开 `append` 不接受该字段，则退化为上文的"什么都不做"：只 `session.append({ type, payload })`，见 §5。）

## 5. 正确的生产者语义，以及普通插件该做什么

**canonical 规则（与版本无关的那部分）**

- 标记是**事件契约的一部分**：生产者在**构造事件时**声明，reader 在**读取时**尊重。生产者的动作只有"声明"一种，**永远不包括"抹除"**。
- 三态语义：显式 `true` = 可忽略（信息性）；`false`/缺省 = 载荷性，reader 不得静默丢弃；字段在契约中缺席（alpha.1 窗口）= 生产者无法表达，由宿主按默认处理——**缺席是一种状态，不是一个需要执行的动作。**
- 归属原则：**谁受益谁声明**。可跳过性是给 reader 的便利，故必须由生产者在事件上如实标注；reader 端不做"猜测式宽容"。

**普通插件经 `Session.append(...)`**

要点在提示里已经给了：**公开 API 面上很可能根本没有这个参数**。这恰好是本题的解法，而不是障碍：

- 如果 `append` 的签名里没有 `ignorable`，那它就不是"你需要管理的参数"，而是**不归你管的东西**——普通插件只负责 append 一个形状合法的事件，标记由事件对象承载或由宿主在落盘/广播时补齐；
- 因此普通插件的最小正确实现是：**不 delete、不补 `false`、不 `as any`**。三件事都不做，就是 alpha.2 下最省事也最正确的答案；
- 反向判据（很好用）：**一个参数不在公开面上，就不可能是一个必须由调用方手工维护的不变式。** 靠类型逃逸去维护它，说明维护者误把内部实现细节当成了对外契约。

## 8. 判定回顾

- 防御代码的命运：**删除**。它防的是一个不存在的字段（E1），依赖一条不可触发且无来源的断言（E2），并在 alpha.2 的恢复语义下把方向做反（E4）。
- 生产者语义：**只声明，不抹除**；标记缺席是状态，不是动作。
- 普通插件：`Session.append` 上没有这个参数，就说明它不该被调用方手工维护——**什么都不做**即正确。
- 方法论：注释同时给出了正确的历史与错误的指令（E5），这正是"由证据判定"的用武之地；走廊的走向（A1-02 移除 → A2-01 恢复）与代码事实指向同一个答案。
