## 1. Split chunks: the entry is not the complete module graph

console-split-chunks.txt records a 200 for the 8.1 kB mermaid-chunk.js entry, followed by 404s for src-BfvxrPJe.js and pie-WAS4IAKB-CQHCQWWM.js. It explicitly states that these referenced siblings were NOT shipped in lib/. The browser resolves relative module specifiers against the importing module's URL, so these requests go to /dsh-attach-input/resources/, not an npm installation or the original source tree. Loading the entry successfully is insufficient: the required static dependency graph must load, and subsequent dynamic diagram imports must also resolve. A missing required dependency rejects module loading; a missing deferred diagram module rejects when that diagram type is requested. The generic dynamic-import error and code-block fallback follow from these missing artifacts, not from Mermaid syntax.

**Build fix:** produce the designated lazy entry as one self-contained browser ESM artifact, with Mermaid and its transitive runtime imports bundled into it. Disable splitting and inline internal dynamic imports with the actual bundler's supported options (for example, Rollup's output.inlineDynamicImports for a single input). Do not externalize Mermaid or its diagram modules. Preserve lazy loading at the outer plugin-to-Mermaid boundary: the plugin still imports this larger file only when needed. Verify emitted output, rather than trusting an option name; disabling splitting alone does not guarantee that external or otherwise unbundled imports disappeared. A valid alternative is to ship and serve the entire emitted dependency graph at the exact expected URLs, but that is not the chosen single-file rollout.

## 2. Windows 403: lexical normalization is not filesystem canonicalization

chunk-route.ts has two case-sensitive string-prefix guards: one for abs and another for file after realpathSync. ci-note.md supplies the decisive production values:

- LIB_DIR: E:\dsh\profiles\web\node_modules\@org\dsh-attach-input\lib
- realpath: e:\dsh\profiles\web\node_modules\@org\dsh-attach-input\lib\mermaid-chunk.js

fileURLToPath converts a file URL to the platform path spelling; it does not canonicalize the filesystem path. On Windows, the resulting drive-letter spelling can be uppercase as shown here; on Linux it yields a POSIX absolute path without a drive letter. path.normalize cleans separators and lexical dot components. On Windows it uses backslashes, but it does not fold drive letters or path components to a common case. On Linux it uses forward slashes and likewise does not change case. join plus normalize therefore retains the root's lexical uppercase E: in abs.

fs.realpathSync resolves the actual filesystem path, including symbolic-link/junction resolution, and its spelling need not equal the spelling supplied by the caller. In this production observation it returns lowercase e:. Calling normalize on that result leaves e: lowercase. This is not a rule that every Windows realpath result must always use lowercase; it is a documented-by-fixture difference between these two observations of the same location. Linux's case-sensitive pathname semantics do not equate differently cased paths, and the supplied Linux test has no spelling discrepancy of this kind. The laptop's green result is consistent with matching observed spelling and does not prove Windows coverage of this failure.

JavaScript String.startsWith compares characters case-sensitively on every OS. Consequently, the realpath guard rejects e: against E: even though they identify the same Windows drive and the file is inside the directory. This is a false containment rejection, not a missing file, bundling failure, CORS problem, or Windows ACL failure. The 403 branch log and the existing file in console-403-windows.txt support that diagnosis.

There is a separate caution in the excerpt: normalize can preserve a trailing separator from the directory URL; blindly adding sep can then create a doubled separator in the prefix. The printed production LIB_DIR has no trailing separator, so this is not the evidenced cause of that failure. The replacement below also avoids relying on trailing-separator spelling.

## 3. Guard repair and module-serving requirements

Use path.relative with the native platform's path semantics rather than a case-sensitive absolute string prefix. Classify a candidate as a strict descendant when the relative result is nonempty, is not exactly '..', does not start with '..' followed by the native separator, and is not absolute. The exact-segment tests avoid rejecting ordinary names that merely begin with two dots. The absolute check matters when Windows paths are on different drives or otherwise have incompatible roots. The nonempty check excludes the directory itself for a file-serving route.

Keep both stages of protection: first test the lexically resolved candidate against the lexical absolute root; then realpath BOTH the root and candidate and test the resolved candidate against the resolved root. Resolve the root once at route setup if its lifetime and deployment model allow it. This compares equivalent representations and prevents a symlink/junction inside lib from authorizing an outside target. Do not remove realpath validation as a workaround. Native path.relative handles the evidenced Windows case-only drive difference and preserves POSIX case sensitivity; lowercasing all paths would incorrectly erase Linux distinctions. This is appropriate for ordinary platform path semantics, not a blanket proof for unusual case-sensitive Windows directory configurations or adversarial concurrent filesystem replacement. The route should serve from a trusted deployment directory; a writable hostile tree requires stronger race-resistant file access design.

**Other essential requirement:** the resource must be served as JavaScript, not an HTML fallback or an attachment response. chunk-route.ts already returns application/javascript; charset=utf-8 for success. Browser module loading applies strict MIME checks. Preserve a successful same-origin GET route at the actual import URL, with complete bytes and a valid browser ESM artifact; an entry returning 200 HTML is still a failed dynamic import. The prefix must also cover every reachable dependency if splitting is intentionally retained.

## 4. Ctrl+wheel conflict: one gesture must have one owner

The reported behavior means both diagram zoom and pane font zoom act on the same wheel event. Neither Ctrl being held nor preventDefault grants exclusive ownership: preventDefault suppresses the browser default action, not other JavaScript listeners. Capture listeners execute along the ancestor path before target/bubble listeners. A pane/global capture listener can resize text before the modal's target or React bubble handler gets a chance to stop propagation. A portal also need not share the pane's DOM ancestry even when it participates in the same React tree. Listeners on the same target and phase can execute in registration order; stopPropagation does not stop other listeners on that same target. A late stopImmediatePropagation cannot undo an earlier resize and can suppress unrelated behavior.

**Ownership rule:** while the zoom modal is active, gestures belonging to it are owned by the modal. The pane/global Ctrl+wheel handler must check modal ownership before mutating font size and return without acting for those gestures. A fullscreen blocking modal can suspend pane font-wheel handling for its entire open lifetime; alternatively, an explicit shared gesture-owner state or reliable event composed-path check can identify modal-owned events. The modal updates diagram scale and prevents browser Ctrl+wheel zoom with a cancelable, non-passive wheel listener where needed. Propagation control can supplement, but not replace, the pane's early ownership check. On close/unmount, remove modal listeners and restore pane ownership, including update/teardown paths.

**Evidence limit:** the fixture has no pane or modal listener source and no event-order trace. Thus capture-versus-bubble and same-target ordering explain how late suppression fails, but their exact targets, phases, framework, and registration order cannot honestly be claimed as observed facts. Inspect those handlers and add an instrumented dispatch trace during implementation. The ownership fix does not depend on guessing their ordering.

### Checks actually performed

In particular, win32.relative('E:\dsh\lib', 'e:\dsh\lib\mermaid-chunk.js') returned 'mermaid-chunk.js', while a C: candidate returned an absolute path. A direct string-prefix comparison rejected the case-only E:/e: difference as expected. A supplemental URL-parser probe confirmed encoded dot-segment normalization; it was not a route integration test and does not establish request-validation coverage.

No browser, bundler, real route integration, real filesystem realpath, or wheel-event regression test was run: the fixture is static evidence and supplies neither runnable plugin/build configuration nor event-handler source. The test matrix above is proposed coverage, not a claim of passing implementation tests. These evidence gaps do not block the reported artifact and Windows root causes, but they prevent verification of a deployed fix or an exact listener-order diagnosis.
