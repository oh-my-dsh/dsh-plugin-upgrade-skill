# S24 The dock that vanished together (calibration answer)

## 1. Culprit attribution

Plugin A (the session-progress strip) is the only crashing plugin. The console error
names it: `TypeError: useSessionPendingInteraction is not a function at
SessionProgressBar (plugin://dsh-external/dsh-ui-progress/...)`. Plugin A destructures
and unconditionally calls two seats that alpha.2's `SessionStandardProps` no longer
provides — `useSessions` and `useSessionPendingInteraction` were removed by the
multi-instance refactor (contract/slots.d.ts now lists only `useConversation`,
`useInput`, `inputActions`). The first removed-seat call throws during render.

## 2. Why plugin B's chips vanish too (co-tenant mechanism)

The input dock is a list slot whose entries all mount under ONE shared
`DrawerErrorBoundary` (see dock-render-tree.md). React error-boundary semantics unmount
the entire boundary subtree when any child throws during render — so the crashing strip
takes the innocent `dsh-paste-input-dock` entry down with it. The attach button
survives because it lives in `conversation.input.left`, a DIFFERENT slot mounted under
a different boundary: same plugin, different subtree.

The decisive experiment proves the coupling: disabling plugin A restored plugin B's
chips instantly. That establishes A's presence caused the unmount; it does not prove B
is fully alpha.2-compatible in every other respect, nor that the strip crash was the
only dock defect.

Reinstalling plugin B could never have helped: B was never broken. Its registration is
intact, its render path uses no standard-kit hooks, and its own try/catch logged
nothing. The colleague's "both plugins were hit by the refactor" theory is half right
for the wrong reason — the kit changed, but only plugin A uses the removed seats.

## 3. The fix (graceful degradation)

```ts
const EMPTY_BY_ID: Record<SessionId, SessionSummary> = {}
const EMPTY_INTERACTIONS: ReadonlyMap<SessionId, SessionPendingInteraction> = new Map()

export function SessionProgressBar(props: SessionProgressBarProps) {
  if (props.session === undefined || props.session === null) return null
  const chat = props.useConversation(c => c.views.get('chat'))
  const legacy = chat?.legacy ?? EMPTY_LEGACY
  const todos = props.useProjection('todos')
  const running = props.session.running
  // ... percent/turn/elapsed/eta derivation unchanged ...

  // alpha.2: both seats removed from the standard kit - degrade instead of throw.
  const pendingBySession =
    props.useSessionPendingInteraction?.(i => i) ?? EMPTY_INTERACTIONS
  const sessionsById = props.useSessions?.(s => s.byId) ?? EMPTY_BY_ID
  const ownPending = pendingKindOf(pendingBySession.get(props.sessionId)?.kind)
  const subPending = subagentPendingState(sessionsById, pendingBySession, props.sessionId)
  const subRunning = subagentRunningCount(sessionsById, props.sessionId)
  // ... render unchanged ...
}
```

`subagentPendingState`/`subagentRunningCount` accept the empty fallbacks and return
zero counts, so the subagent indicator reads as absent. **What degrades**: the amber
pending-attention state and the subagent indicators. **What keeps working**: running
state, todos percent, tool name, elapsed/ETA, token usage — all from
`session`/`useConversation`/`useProjection`, which survive.

**Why degradation must be silent**: a throwing dock tenant unmounts every co-tenant
entry under the shared boundary — a missing indicator is cosmetic, a throw is a
multi-plugin outage. Degradation must never escalate to a throw.

**Full function later**: subagent pending/running state now lives in the `uiSession`
service's status domain (`sourceFor(owner)` / `PendingInteractionDomain`); the plugin
re-adds detection by integrating with that service through its own fiber rather than
the dock standard kit.

## 4. Multi-tenant hygiene

**Tenant-side**: destructure defensively (optional chaining + stable module-level empty
fallbacks whose reference identity never moves) so a missing seat degrades instead of
throwing. A tenant may additionally wrap its own render in a local error boundary so
even a genuine bug unmounts only its own entry.

**Host-side**: mount each dock entry under its own error boundary, rendering a small
"entry failed" placeholder for the crashed one. Trade-off: per-entry boundaries add
nesting and make cross-entry layout coordination harder (the dock is one visual row),
and a half-rendered row may look worse than an empty one — presumably why alpha.2 kept
one shared boundary. The isolation fix still shifts the blast radius from "everyone" to
"the culprit", which is the right default for a multi-tenant slot.
