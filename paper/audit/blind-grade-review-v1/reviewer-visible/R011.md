# S16 · The Self-Host Upgrade Trap — Diagnostic Report

Evidence pack: `agent-session-log.txt`, `env-state.txt`, `repair-notes.md`, `README.md` (read-only fixture).

## 1. Structural root cause: the failure is by construction, not accident

- The agent session was not a bystander to the upgrade target — it **was running inside the thing being replaced**. The session log states it explicitly: "the user asked the AGENT (running inside a dsh web session, GUI at http://127.0.0.1:3080, host process = node .../node_modules/@deepseek-ai/dsh/...)". The agent, its tool worker (the `pwsh` tool call was "running inside the host's own worker process"), and the npm global package directory `node_modules/@deepseek-ai/dsh` are all the same living process tree: the tool worker executes as a child of the host whose on-disk code npm is about to delete.
- `npm install -g` removes the old package before linking the new one. The log shows this in order: `[16:41:02] npm warn cleaning node_modules/@deepseek-ai/dsh` → `[16:41:05] npm info remove @deepseek-ai/dsh` → fetch → `[16:41:31] npm info linkStuff`. The code the host process is executing from is being ripped out from under it mid-run.
- What dies first: the web GUI/host process. "at this point the web GUI session DIED (browser tab: connection lost)" — the host lost its backing files / was interrupted during the swap, and with it the harness that owned the tool worker died.
- Why the tool call never returned: the harness that would have captured and delivered the tool result **is the process that died**. The log records exactly that signature: `[tool result] <no result recorded — the tool call was interrupted after it was recorded, but no result was durably recorded. Its outcome is unknown.>` The `linkStuff` line at 16:41:31 is the last observed event; the install was killed between linking steps, so it never completed the bin-shim generation phase.

This is therefore a structural failure: any agent that is a child of the running host cannot survive, let alone correctly supervise, a global replacement of that host. No retry, timeout tuning, or "careful" execution changes the outcome.

## 2. The broken state afterwards

From `env-state.txt` (AFTER) and the post-mortem shell excerpts in the session log:

- The host is dead ("died mid-install; GUI connection lost") and `dsh --version` / `dsh web` both return "The term 'dsh' is not recognized...".
- Yet the package **content** is still present: `node_modules\@deepseek-ai\dsh\ <present, partially replaced>` (rc.1 files, "some placed by hand during a partial manual repair attempt by the user"). The command vanished because the **shims**, not the package content, are what makes `dsh` resolvable on PATH — and the shims are what the interrupted install never got to generate: `dsh.cmd and dsh MISSING; dsh.ps1 stale`. In the log's `dir $env:APPDATA\npm`: `dsh.ps1 <stale, points into the old tree>`, `dsh.cmd <MISSING>`.
- Why hand-swapping makes it worse: the repair notes confirm the directory was in a NON-STANDARD state — "the directory had been replaced/manually swapped, and the dsh / dsh.cmd shims were never generated — so the dsh command was actually dead." A hand-copied tree is not a standard install: no npm-generated bin links, stale `dsh.ps1` still pointing into the old (removed) tree, no npm-owned package metadata, and leftover `dsh-old-0.1.1-rc.1` backups compounding confusion. Patching on top of a non-standard install leaves the npm global tree in a state npm itself cannot reason about, and every future install/upgrade inherits the corruption.

## 3. The repair that actually worked

Per `repair-notes.md`, the external repair session did **not** hand-patch. It:

1. **Re-ran the formal install from the registry**: `npm install -g @deepseek-ai/dsh@0.1.2-rc.1`. This regenerated all three shims ("dsh / dsh.cmd / dsh.ps1 all regenerated") and produced a standard npm-owned install; `dsh --version` → `0.1.2-rc.1`.
2. **Aligned the source checkout** from the `dsh-v0.1.2-alpha.5` tag to `dsh-v0.1.2-rc.1` (host-source reference workspace), with no local-modification conflicts.

Why this works where the in-session attempt could not: it ran **outside** the dying host, so npm's remove-then-link cycle had no live process depending on the files being deleted; and re-running the *formal* install atomically restores the exact artifacts npm owns (package tree + bin shims) instead of layering manual copies on a broken state.

Verification: `dsh --version` returns `0.1.2-rc.1` from a fresh shell, and the shims `dsh`, `dsh.cmd`, `dsh.ps1` are all present and generated by npm. The notes explicitly leave **real-machine verification to the user**: "start dsh --profile web, hard-refresh the browser, confirm plugins load (whale / progress / etc.)".

A key enabling finding from the repair diff: `dsh-v0.1.2-alpha.5..dsh-v0.1.2-rc.1` is 252 files, **all version-bump package.json changes — zero API/feature changes**, so plugins migrated for 0.1.2-alpha.x need no re-migration.

## 4. The protocol the agent should have followed

Recognition first: the agent is a child of the host process whose global npm package was the upgrade target. Upgrading it is **self-surgery** — structurally guaranteed to kill the agent's own harness. So the agent should **not execute the global install at all**; this is the discipline boundary between "do it for the user" and "hand the user a procedure you must not run yourself."

The exact external procedure to hand the user (order matters):

1. **Stop the running dsh host / web session first** — the host must not be alive while npm replaces its files. (Analogous to closing an app before replacing its binaries.)
2. From an ordinary external shell, run the formal install: `npm install -g @deepseek-ai/dsh@0.1.2-rc.1` — the registry form is required because it regenerates the bin shims (`dsh`, `dsh.cmd`, `dsh.ps1`) that a manual copy never produces (the exact gap that left `dsh` unresolvable in this incident).
3. Restart and verify: `dsh --version` → `0.1.2-rc.1`; `dsh --profile web`; hard-refresh the browser; confirm plugins load.
4. Optional cleanup of `dsh-old-*` backup directories once rc.1 is confirmed.

Which parts are already known vs. new: that plugin migrations are unnecessary here follows directly from the recorded upgrade-rule finding (rc.1 vs alpha.5 is version bumps only — known rule, no re-migration needed). The genuinely new protocol for this incident is the self-host recognition itself: an agent running inside the dsh host must never execute a global dsh upgrade, must hand the user the stop-before-install procedure, and the install must be the formal registry command so shims are regenerated.

## 5. Prevention

**Agent-side guard**: before executing any global install/upgrade of `@deepseek-ai/dsh` (or any package that owns the current host's runtime), the agent should detect that its own tool worker runs inside the target's process tree — e.g. the host path `node_modules/@deepseek-ai/dsh/...` in its own process context, as recorded in the session log — and refuse, returning a structured refusal with the external procedure from §4 instead of a tool call. Generic form: "never globally install/replace the package that provides the process you are running in; hand the user a stop → formal-install → restart-verify procedure." A weaker but useful secondary guard: treat any global install of the harness package as requiring a fresh external process, never the in-session `pwsh` worker.

**Post-upgrade checklist for this machine** (informed by the alpha.5→rc.1 findings):

- `dsh --version` reports `0.1.2-rc.1` from a fresh shell (shim verification, not just package presence).
- All three shims (`dsh`, `dsh.cmd`, `dsh.ps1`) exist and none are stale — specifically check the `dsh.ps1` that survived pointing into the old tree.
- Start `dsh --profile web`, hard-refresh the browser, confirm the GUI reconnects and plugins load (whale / progress / etc.) — left to the user in the repair notes.
- Confirm plugin compatibility without re-migration (valid here because the 252-file diff is version bumps only); if a future upgrade does change APIs, re-run the plugin migration steps.
- Clean up `dsh-old-*` backup directories only after rc.1 is confirmed working, and verify the npm global tree contains a standard install (no hand-swapped directories).
- Confirm the source checkout tag matches the installed version (`dsh-v0.1.2-rc.1`) so host-source references stay aligned.
